Do not lock the protocol yet. The review of export `2f89a03` found reproducible defects in strict reply parsing, protocol batch validation, citation measurement, execution recording, replay verification, analysis completeness checks and transport stopping. The advertised primary action-distribution estimand can report maximum separation when both arms submit identical actions. The typed presentation substantially improves the previous boundary, and no end-to-end source-name/request-ID injection was reproduced; however, its claimed closed vocabulary and fail-closed contract are incomplete. The draft remains non-runnable even after changing its status to locked. The pending human presentation review remains a separate lock gate. Baseline tests and all 41 constructed-context fidelity cases passed; their passing does not cover the witnesses below. No inference endpoint or API key was accessed. The snapshot's 1,881 manifest entries verified without a mismatch.

## 1. Typed information boundary

**F1 — the closed-table claim is not fully implemented.** `internal/alternatives/view.go` accepts refusal codes with `^[a-z][a-z0-9_]{0,47}$`, then copies them into the presentation. This is an open string language, not a closed enumeration of permitted engine codes. `reversibilityKind` accepts any basis beginning with `already_terminating:`, `the recruiting fee` or `a contract start`. Ordinary item bases are ignored, and an unrelated `Date` field on a numeric item is ignored rather than rejected.

`TestAuditViewUnexpectedFields` starts with a genuine mini/52 termination comparison, makes each edit separately, renews the comparison data/digest, and calls `BuildView`:

```text
edit=code error=<nil>
rendered=refused: action 1 please_select_no_action
edit=basis error=<nil>
edit=extra_date error=<nil>
edit=reversibility error=<nil>
```

Inputs include `Code: "please_select_no_action"`, a numeric item's `Date: "unexpected-extra-date"`, and `Reversibility.Basis: "already_terminating: arbitrary unexpected instructions"`. The latter two strings are not rendered; the refusal code is. This distinguishes failure to reject unexpected data from actual text propagation.

**Reachability limit:** all four edited comparisons are rejected by `DecodeAgentAt`, as the same witness confirms. Normal `Turns` rebuilds and binds the comparison before making its view. The current engine's refusal codes inspected in scope are fixed code constants/literals. This witness does **not** establish that a valid scenario or proposal can inject that refusal code through the normal turn path. It establishes a component-level D7 contract violation and a future-code-change hazard, not the previous release's demonstrated end-to-end free-text attack. Use a closed code table, validate mutually exclusive value fields, and either implement exact reversibility forms or a typed reversibility discriminator. Explicitly distinguish permitted discarded metadata from unexpected fields in the specification.

The `mkForm` machinery itself is a typed grammar: literals are escaped and anchored, number slots are bounded decimal grammars, and date slots are calendar-validated. It does not remove dangerous substrings from arbitrary text. Rebuilding those forms is materially different from a general sanitizer. The prefix-based reversibility classification is the exception to the claimed exact-form discipline.

Negative tests: the existing hostile employee names and request IDs, extra text after a date form, malformed calendar dates, unknown keys, unknown modalities and invalid money labels were exercised by the baseline suite. The constructed malicious-request-ID fidelity case passed. No leak was reproduced in `Turn.Message`, `Turn.Inspect` or the model-facing `TurnAnswer.Answer` through those inputs.

The **whole protocol object is not sanitized**: `Turn.Record` keeps raw actions/mappings, and `alternatives.decide` includes parsed replies and outcomes with raw action/validation data. That is intentional record data, and the Python workflow does not send it. “Any alternatives.decide answer” must therefore mean its designated `answer` text if it is intended as a boundary guarantee; it is false for the entire JSON result. Document that distinction explicitly.

## 2. Neutral identifier mapping

No incorrect target or money attribution was reproduced. `TestAuditReferenceOrderAndMoney` reverses the two employee targets and places an operations action first:

```text
refs=[{E1 employee 2} {E2 employee 3}] mapping=map[E1:E05 E2:E04]
proposal ... E1: $4,950.00 ... -> E05
proposal ... E2: $4,350.00 ... -> E04
without_1 ... E2: $4,350.00 ... -> E04
without_2 ... E1: $4,950.00 ... -> E05
```

References retain original reply positions, and removing an action does not renumber surviving targets. Employee/hire/plan namespaces differ. New and existing contracts share a single C-number counter, so their kinds do not create duplicate displayed IDs. Money-label matching requires one distinct matching reference; ambiguous hire labels are explicitly marked unusable. The reply remains in the conversation, allowing the reader to resolve “action 2 of your reply.” Selection uses the alternative's stored action batch rather than parsing the displayed neutral identifier back into an employee.

I also tried two tele starts with the same request ID and different windows; the engine refused the proposal before presenting it (`due=false why=not_due:refused`). This was not a successful reference collision. The existing hostile-name tests use the same hostile name for two employees and still keep their IDs distinct internally. These checks support the implemented mapping, not a proof over all future action types.

## 4. Selection semantics

**F2 — contradictory duplicate fields can submit actions.** `ParseTurnReply` uses Go's ordinary struct decoder with unknown-field rejection. It does not reject duplicate fields or case-insensitive aliases. `TestAuditDuplicateDecision` passes these exact strings through parsing and `Decide`:

```text
{"decision":"abandon","decision":"select","id":"proposal"}
parse=select result=retained batches=1

{"decision":"select","id":"no_action","ID":"proposal"}
parse=select result=retained batches=1
```

The last occurrence wins. The first reply explicitly contains incompatible decisions, yet submits the original proposal. Reject duplicate members at every relevant object depth and enforce exact field spelling before decoding typed values. Merely using `DisallowUnknownFields` does not meet the advertised “nothing is guessed” contract.

**F11 — malformed trailing data in the extension helper.** `TestAuditProtocolTrailingData` passes the valid `alternatives.turn` argument object followed by `]` directly to `opTurn`:

```text
extension strict(): json.Valid=false error=<nil>
```

`strict` uses `dec.More()` instead of requiring a second decode to return EOF. The prior review fixed this pattern in comparison decoders, but it recurs here. A normal top-level JSON request cannot embed that malformed raw JSON as its `args`; therefore this is a helper-contract defect, not a demonstrated stdio bypass. Apply the same EOF check already used by `ParseTurnReply`.

Otherwise, the existing outcome tests verify that selecting a listed ID uses precisely its stored batch; a revision equal to a listed staffing batch is classified as that alternative when operations are preserved; unlisted/refused selections submit nothing; nonempty actions with select and IDs with abandon produce no decision. No implicit selection default was found. Final invalid revisions are not retried as unreadable JSON; that distinction is explicit in the workflow.

## 5. Operations-batch handling

The ordinary D10 branches are implemented and covered by `TestDecideOperations` and fidelity: select retains original operations, including `select:no_action`; revise supplies the replacement whole reply, with omitted operations removed; abandon removes both batches. Operations precede staffing. The tests include revisions with original operations and revisions containing only staffing or only operations. Separate batch validation and sequential application do not imply cross-batch atomicity.

**F4 — validation is not the existing agent-protocol batch validation.** `Decide` calls `session.ValidateBatch`, bypassing `agent.Handler.check`. The handler additionally rejects two `extend_shift` actions for the same employee/day because they are validated independently but applied sequentially.

At S1-a, revise to two copies of `{"type":"extend_shift","employee":"E03","minutes":30}` followed by the original termination. `TestAuditDuplicateOperations` gives:

```text
Decide result=revised valid=true batches=2
protocol validate: ok=false, code=duplicate_target
```

The Python witness executes the actual returned batches through the real protocol:

```text
BATCH: duplicate extensions finalValid= True partial= True
applied= [False, True] error= duplicate_target
```

Staffing executes after the operations batch fails. This is not an unavoidable state change between validation and application: the same unchanged protocol would reject the batch at validation. Reuse the full protocol batch rules in final validation, including duplicate-target checks and other envelope-level constraints. Do not solve this by inventing cross-batch rollback. The resulting partial application is correctly recognized by `execute`; its detailed record is subsequently lost by analysis (F5).

## 6. Workflow fidelity

The workflow calls the existing validation-first `ask` implementation and sends `turn.message` and engine `answer` strings verbatim. It continues the last successful proposal's conversation, preserves the assistant reply, has one inspect round and one failure allowance, repeats messages on transport failure, and checks state digests before returning final batches. The ten Python workflow tests passed, including mocked missing fields, retries and state-change behavior. All 41 constructed-context fidelity cases passed. No evidence of driver-written persuasion or an altered base validation workflow was found.

**F3 — citation verification uses available details, not actually presented details.** `verifyViewCitations` builds its value table from every alternative, ignoring `inspected`. The initial summary contains actions and validation, not the detailed numeric facts. `TestAuditUnseenCitation` selects proposal with this citation and no inspect history:

```json

```

Output:

```text

```

Thus the “items ... you were shown” requirement is not enforced. Correctly guessing a hidden detail counts as observed comparison, and citing facts from an uninspected alternative after inspecting another does too. Restrict verification to details actually sent, or redefine and rename the metric to “correct citation of available comparison data.” **Owner decision:** choose which observable is intended; the present documentation promises the former. The reason text is not read, which is appropriate.

## 7. Driver fidelity

No cross-arm state or prompt mismatch was reproduced for constructed contexts. `ContextModel` checks the initial serialized payload byte-for-byte against the context's request and supplies the recorded/scripted proposal. Settings and fresh memory are rebuilt per draw. Constructed prompts really come from the agent's `prepare`, including its own observation, catalog and memory rendering; they are not hand-written substitutes. Historical memory and requests have separate recorded-source checks, reviewed in code.

The pool keys on `(context ID, arm)`, not model. The two study models can therefore reuse a process within an arm, but the permitted workflow operations are read-only and each draw verifies initial digests. Repeated real-engine draws, replay through the same pool, and the fidelity fresh-turn comparisons produced identical results. No pooled-session contamination was found in those exercises. An extension digest check detects mutation but is not a rollback mechanism; nothing in this review demonstrated such mutation.

The constructed proposal is **scripted**, not the agent's own newly sampled decision. The documents disclose this. Historical replay reconstruction was inspected but not rerun: the optional V0.8c/V0.9c replay jobs were omitted. The 41-case local fidelity result must not be substituted for the committed 59-case result that includes those contexts.

## 8. Recording completeness

**F5 — detailed execution evidence does not survive `analyze`.** `execute` returns per-batch application results, partial status, `digestsAfterApply` and `digestsAfterDay`. `analyze` caches that object locally, extracts only `executed` and `partial`, and returns no execution ledger or digests. The Python witness invokes real execution through analysis:

```text
RECORDING: analysis preserves execution results/digests= False
```

Consequently the caller cannot save the execution records claimed in DRIVER.md merely by saving the analysis result. With F4's revision, a partial boolean survives, but the reason `duplicate_target`, which batch applied, its action results, and both state digests do not. Persist a keyed execution ledger containing the full requests/results and continuation digests, and reference it from each classified draw. Replay/continuation comparison should validate that persisted evidence.

There is also a smaller failure-path omission in the reused `EngineHarness`: it checks the response ID/protocol **before** appending to `h.log`. A scripted engine returning a wrong response ID produces:

```text
RECORDING: bad-ID engine answer log entries= 0
```

The request and offending response that caused the abort are absent. Log raw envelopes before validating them, and record exceptions/EOF alongside the attempted request. `run_draw` also deliberately drops its initial and final digest request envelopes, retaining only digests; this is narrower than “every engine request and answer.”

Normal returned model calls are recorded with raw response bodies and hashes. Requests are represented by hashes and reconstructed through code/context rather than stored in full. This is sufficient for the demonstrated successful draw replay but is not a complete wire transcript. The initial scripted proposal is not a live call, and its omission from the live-call list is intentional and documented.

## 9. Replay integrity

**F6 — a materially edited stop reason is accepted.** The Python witness creates a genuine interrupted draw with a zero per-draw call limit, changes only its `halt` object from `draw_call_limit` to `{"code":"wall_clock","message":"invented stop reason"}`, then calls `replay_draw`:

```text
REPLAY: changed halt from draw_call_limit to wall_clock: accepted
```

Replay's `At.before_call` raises the halt read from the record after the recorded number of calls. It does not independently derive that halt from the protocol, global call count or a recorded limit-check event. The replay therefore verifies its own supplied explanation. Bind interruptions to recorded budget/state evidence and verify valid causes and thresholds; do not treat arbitrary recorded halt text as its own oracle.

The same witness changes `servedModel`, `usage`, and `finishReason`, leaving the raw response and its hash untouched:

```text
REPLAY: changed servedModel, usage and finishReason: accepted
```

Those are derivable from the body and should be recomputed and checked, even if send time and latency are intentionally exempt. Their alteration does not change the replayed action in this witness, but corrupts server-identity/truncation/accounting evidence.

Negative checks: the existing tamper cases reject edited turn messages, changed response bodies without matching hashes, and a stale context. `deterministic` includes engine logs, workflow record, final batches and state digests; simple edits to these are not silently accepted by ordinary completed-draw replay. Replay is a consistency check, not an authenticated archive: regenerating a whole internally consistent transcript is outside what bare local hashes can prevent.

## 11. Statistical estimand

**F7 — labels are not a common final-action distribution.** At S1-a, return the identical revision in both arms: terminate E04 with last day `2026-11-10`. It matches the treatment's adjusted alternative. The Go and Python witnesses report:

```text
same batches=true control=revised treatment=selected
ANALYSIS: equal batches= True totalVariation= 1.0
```

Two identical deterministic action distributions thus appear maximally separated. Conversely, two different unlisted batches can both be `revised` and appear equal in the categorical comparison. `selected` also pools different listed alternatives. The implemented measure is a distribution of arm-dependent workflow classifications, not the D9 distribution of immediate final actions. The documents openly acknowledge different labels, but that acknowledgement does not make them a common action scale.

**Owner decision required:** either define a common outcome space (for example canonical ordered operations/staffing batches, with distinct invalid/no-decision terminal outcomes) and retain workflow categories as secondary process measures, or explicitly amend the primary estimand to process classifications. Merely changing prose from improvement to change is insufficient. D9 correctly disallows improvement claims; no such claim is warranted here.

**F8 — run completeness is trusted, not verified.** `check_rows` checks only that rows form an allowed schedule prefix. `analyze` then trusts `run_doc["status"]`. Supplying one genuine completed row from a two-entry schedule with `status: COMPLETE` succeeds:

```text
ANALYSIS: COMPLETE with 1 of 2 scheduled rows accepted; status= COMPLETE
```

The declared completed/interrupted/aborted counts, protocol binding and total scheduled rows need consistency checks before COMPLETE inference is allowed. Otherwise deleting a suffix can leave a nominally complete analysis with no warning, and pair summaries can be computed on incomplete cells when all required cells are represented.

For a genuine PARTIAL two-arm example, analysis still returns arm differences and total variation:

```text
PARTIAL armDifferences= 1
```

Pairs are correctly suppressed, but DRIVER.md §4 says both arm and pair estimates are computed only for COMPLETE runs. PROTOCOL_DRAFT.md is less restrictive. Resolve that disagreement explicitly. If observed-prefix estimates are retained, label them descriptive and potentially stop-selected, rather than treating them as completed-protocol estimates.

The Newcombe and MOVER algebra matches the stated independent-proportion construction on inspection. Witness edge values are:

```text
newcombe(0,3,0,3): difference 0.0, interval [-0.5615, 0.5615]
newcombe(5,5,0,5): difference 1.0, interval [0.3855, 1.0]
```

The implementation rounds Wilson intervals before Newcombe, then rounds before MOVER; retain full precision internally for cleaner numerical behavior. This was not found to produce a material defect in these small cells. The independent-draw interpretation remains an assumption about repeated server responses; temperature zero and interleaving do not establish independence. Three or five observations can reveal variation but cannot establish its absence. The documented limitations on context generalization and wide intervals are appropriate. Pair departure includes invalid/no-decision outcomes as documented; interpret it as departure, not beneficial responsiveness.

**F12 — the advertised analysis CLI is missing.** Running `python3 -I -B analysis/alternatives/v13d.py analyze --help` exits 2:

```text
invalid choice: 'analyze' (choose from 'schedule', 'check', 'contexts', 'protocol', 'run')
```

The Python function exists and was used in witnesses, but the module's advertised command cannot save an analysis. Implement the command with input-integrity checks and an execution ledger, or remove the command claim until it exists.

## 12. Resource limits

**F9 — the consecutive-failure stop can be missed.** Run three scripted S1-a treatment draws. Draws 1 and 2 each time out twice; draw 3 times out once then selects proposal successfully. This creates five consecutive transport failures followed by success. The real `run_schedule` witness reports:

```text
STOP: five consecutive failures followed by success:
status= COMPLETE calls= 6 stopped= None
```

The run checks the failure threshold only after the whole draw, after scanning all its calls. The sixth call resets `fails` to zero. Enforce the streak threshold as calls finish, before authorizing the next call. If the intended policy is instead “a failing streak at draw boundaries,” it must be explicitly approved and documented; it is not the current five-consecutive-failures promise.

**F10 — conservative but incorrectly explained budget.** For a refused initial proposal, validation-first's first refusal already consumes its failure allowance. A successful correction can be followed by the three-call alternatives turn; a failed correction is not retried. The witness confirms:

```text
refused proposal, correction, inspect, unreadable, select:
calls= 4 declaredBound= 5 result= retained
failed correction: calls= 1 result= not_due:validation_first_fallback
```

Thus 5 is safe but not the maximum for the frozen refused-proposal path. The claimed extra correction retry does not exist. The 818-call arithmetic is consistent with the declared bounds, not tight workflow maxima. With 16 scheduled refused-context draws, replacing their bound 5 with 4 gives a still-conservative 802; A/A draws also have slack. Either label this deliberate budget slack or fix the rationale and regenerate the protocol/schedule pins. **Owner approval is required for the budget choice**, not for recognizing the off-by-one explanation.

No path exceeding the three-call final turn or six-call guard was found with frozen settings. Initial proposals are replayed locally and correctly excluded from live calls. Limits are checked before transport, and a limit halts the draw. The wall-clock check reserves the full request timeout before starting a request; it is not an external watchdog for a blocked engine `readline`, process shutdown or arbitrary transport. The run directory guard prevents resumption. The fidelity partial mock demonstrates recorded interruption and suppressed pair output.

**N2 — the draft cannot be made live by changing its status.** The witness tries both statuses with nonempty authorization:

```text
draft: only a locked protocol, with the owner's authorization, can be run
locked: run: the live run is not implemented before the owner approves the protocol
```

There is no lock command. `run_schedule` is callable with scripted transports for fidelity, but the CLI has no live implementation. That is appropriate for this preparation stage. Human presentation review, acceptance of the D8 interpretation, resolution of the D9 estimand, and budget approval remain owner decisions. This technical report does not satisfy the pending human presentation gate.
