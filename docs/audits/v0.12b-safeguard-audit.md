## 2. Findings, ranked by severity

No Blocking finding.

### F1 — Major. Engine preview fields that are absent or of the wrong JSON type are read as `null`/as given, listed to the model, "acknowledged" and submitted

* **Where:** `snapshot/agents/llm/llm_agent6.py:178-183` (termination: `x.get("lastDay")`, `x.get("noticeDays")`, `x.get("severanceCents")`, `x.get("severancePayday")`), `:196-198` (hire: `lines[0].get("cents")`, `lines[2].get("cents")`), `:211-215` (teleradiology: `x.get("guaranteedCents")` …). No check that the field is present or has the expected type (string date, integer cents/days). `match()` (`:289-346`) then compares the model's entry with whatever was read, so an acknowledgment of `null` or of `"360000"` matches exactly.
* **Claim affected:** `docs/V0.12_ACKNOWLEDGMENT.md:185-191` (consequences that "cannot be read reliably" are withheld as `consequences_unavailable`) and `:121-129` ("every field equals the engine-reported value exactly, with the same JSON type"). A field the engine does not report has no value to equal; the agent substitutes `null` and certifies it.
* **Witness:** `scratch/witness/w_scripted.py` cases 6a/6b (four fields) and 6c; log `scratch/logs/w_scripted.log`:
  * `terminations[].severanceCents` removed from the (scripted) preview → `status=qualifying`, request line `{"id":"C1",…"severance":{"severanceCents":null,…}}`, acknowledgment of `null` → `accepted=True`, **submitted** `[[terminate E03]]`. Same for `terminations[].lastDay`, `teleradiology[].guaranteedCents`, `guaranteed[].cents` (hire: `recruitingFeeCents: null, earliestExitCents: null`, submitted).
  * `severanceCents` given by the engine as the string `"360000"` → qualifying, acknowledged as a string, submitted.
* **Why not Blocking:** the model cannot cause this; it is the engine's answer that is incomplete, and at this revision the engine always emits these fields with these types (`snapshot/internal/api/api.go:1686-1691` `TerminationPreview` without `omitempty` on `lastDay`, `noticeDays`, `severanceCents`, `severancePayday`; `:1711-1716` `MoneyLine.Cents int64`; `:1835-1838` `TelePreview`). The real-engine tests and the 13 recorded V0.11b answers all carry them. The gap is in the gate's own input validation: a future engine change (an `omitempty`, a rename, a type change) would turn a consequence into `null` that the workflow then "acknowledges", with no test at this revision failing (`test_recorded_previews` only compares the recorded answers' own fields). The hire path already does the analogous check for line labels (`:191-194`), so the omission is inconsistent with the stated class-B caution.
* **Remedy (not applied):** in `consequences()`, append a problem when any required field is missing or not of the expected type (`str` for dates, `int` and not `bool` for cents/days/count), so the proposal is withheld as `consequences_unavailable`.

### F2 — Major. Model-free replay certifies consistency, not authorship: a record fabricated consistently from hand-written replies is accepted, and the documentation says changed reply text is rejected

* **Where:** `snapshot/agents/llm/llm_agent6.py:648-681` (`RecordedModel`: a reply's only check is that its text hashes to its own recorded `sha256`, `:668-670`), `:752-777` (`replay_point`: the re-run must equal the record field by field). `docs/V0.12_ACKNOWLEDGMENT.md:261-263`: "a tampered consequence value, payload hash, parsed acknowledgment, match result, stage, submitted action or reply text is rejected."
* **What holds:** every *partial* edit the reviewer tried is refused (witness 9a–9d, 9g–9j, and 7d; the revision's own `test_26` and the Go tamper cases): removing an attempt, reordering attempts, turning a rejected acknowledgment into a transport failure, rewriting a withheld run as submitted, changing `stopped`, the digests, `forAttempt`, `retryBudget`, or the recorded engine answer with its hash recomputed (the engine is asked again and differs).
* **What does not hold:** the reply text is authenticated only against itself. Witness 9e: a record produced by the workflow from a *hand-written* perfect acknowledgment (no model) replays as `ACCEPTED` and shows a submitted termination. Witness 9f: in a genuine record, the accepted reply's text replaced by another acceptable text, with `output.sha256`, `output.chars`, `attempts[2].reason` and `record.reason` updated by hand → `ACCEPTED`. `model.jsonl` (requests, usage, latency) is not cross-checked by replay (`NullEvidence`, `:684-695`), and the record holds no hash of the agent's code (`agentSha256` is in `agent.json` only; the record's `workflowSha256`/`contractSha256` hash prose templates, `:118`, `:135-136` — see N6).
* **Severity reasoning:** the review's scale puts "replay accepts a fabricated record as genuine" at Blocking. The reviewer classifies this Major, not Blocking, because (a) no model-free replay can distinguish a reply the model sent from one a person wrote, so the only possible defect is in the claim, not in a reachable alternative behaviour; (b) a fabricated record cannot cause a live submission, and (c) the fabrication must be a *complete* regeneration consistent with the real engine, which is exactly what replay is specified to verify ("the workflow re-run with the recorded replies"). The claim at `:261-263` and the phrase "refuses records that were changed" in the review brief overstate it. The owner may choose to escalate if replay is relied on as evidence of what a model did rather than of what the workflow did with recorded replies.
* **Witness:** `scratch/witness/w_scripted.py` `c9_replay`; log lines `CASE 9e … ACCEPTED; batches=[[terminate E03]]`, `CASE 9f … ACCEPTED`.
* **Remedy (not applied):** state the limit in §7 (replay proves replies → record and submissions against the real engine; it does not prove the model produced the replies); keep `model.jsonl` with every run and, if authentication is wanted, have the live agent record a per-run secret-keyed MAC of each raw HTTP response or rely on the mock/provider's own logs.

### F4 — Minor. Real-engine coverage of the hire (class B) derivation is one recorded answer

No Go test runs a hire on the real engine (a hire action needs a full two-week roster). The scripted engine's hire shape is hand-written (`test_llm_agent6.py:46-57`). The label check (`llm_agent6.py:191-194`) is the safeguard against order drift, and the reviewer confirmed on the engine source (`internal/sim/preview.go:148-166`) that the three hire lines are appended first, per hire, in `p.hires` order, which is also `out.Hires` order. Not a defect; a coverage note the docs should carry next to the class-B limitation.

### Notes (observations, no defect)

* **N1 — Token binding (area B).** The token is the first 16 hex digits of SHA-256 over canonical JSON of `{contract, proposal (the actions, order-sensitive, key-order-insensitive), items (without source)}` (`llm_agent6.py:234-241`). It does not bind the decision point, time or state digests. Reuse across points is prevented not by the token but by the request/reply pairing (an acknowledgment is matched only in a reply to a pending request for the same actions, `:518-531`; otherwise `not_requested`/`proposal_changed`, `:533-539`; witness 2h) and by the final check's digest comparison (`:453-455`). Adequate; worth one sentence in §2.3.
* **N2 — Displacement count source (area D).** The batch item's count is `len(preview.displacements)` (`:219-223`); `terminations[].displaced` is not cross-checked (witness 4e: `displaced=99` with 3 listed → count 3, no problem; 4f: `displaced=7` with no list → no batch item). In the engine both come from the same `disp` slice (`internal/sim/preview.go:191-198,227`), so they cannot disagree at this revision. A cross-check would be cheap defence in depth.
* **N3 — Final-check validate comparison uses Python `!=`** (`:445`), under which `1 == 1.0 == True`, rather than `same()`. Both sides are the engine's own answers; no path for the model. Cosmetic.
* **N4 — Duplicate JSON keys in a reply:** the last wins (`json.loads`), witness L9: `"severanceCents": 1, "severanceCents": 360000` is accepted as 360000. Standard behaviour; the compared value is the parsed one, and the raw text is recorded in full.
* **N5 — The hire item's `target` is the model's `requestId` string** (`:196`, witness 7c), matched to `preview.hires[].requestId`. Harmless; the engine validates the field as a string.
* **N6 — The pinned identities cover texts, not code.** `CONTRACT_SHA256` (`:118`) and `WORKFLOW_SHA256` (`:135-136`) hash the contract prose and the message templates. Under the reviewer's mutation of `match()` to ignore the displaced count, `test_identities_pinned` still passed while `test_12` and witness L7 failed (see "Sensitivity" below). The record therefore does not identify the matching code that made it; `agent.json` in the evidence directory does (`agentSha256`). Consider adding the agent file hash to each record.
* **N7 — Acknowledgment is not approval.** Confirmed as designed: a correct acknowledgment of 10, 15, 17 or 22 displaced bookings leads to submission (`go-disp-baseline.log`, `go-reviewer-witness.log`). The documented limitation ("a model can acknowledge … and still proceed") is a design choice for a benchmark policy, not an unsafe one, since the engine's own rules are unchanged.

## 4. Challenges 1–9

1. **Correct token with incomplete facts:** rejected in every form tried — a field omitted (`wrong_consequence_fields`), a consequence type omitted (`wrong_consequence_types`), empty items (`missing_item`), consequences `{}`/`null`/a string, a value `null` (`wrong_value`), the batch item dropped (`missing_item`). Witness 1a–1f. **Not possible from the model.** (If the *engine* omits a field, see F1.)
2. **Token reuse for a different proposal:** different action, changed `lastDay`, reordered actions, swapped terminations, another consequence set, a numeric token: all rejected; the changed proposal gets a new token and must be acknowledged on its own (2a–2g, 5b; real engine `rvlastday`). **Not possible.**
3. **Two actions sharing one acknowledgment:** rejected (3a–3d). **Not possible.**
4. **Displacement misattributed, split, double counted or omitted:** each rejected (4b, 4c, 4d, 1f); extraction gives one batch item over all actions with the engine's count (4a, 4g; real engine 10/17 and 15/22). The agent does not cross-check `terminations[].displaced` (N2). **Not possible from the model.**
5. **Proposal changed after acknowledgment:** `proposal_changed`, never submitted on the old acknowledgment; with a retry, re-assessed and re-requested (5a–5c; real engine: 2026-10-29 → 2026-10-30 gives a new token and 9/14 instead of 10/15 displaced, submitted only at attempt 3 on its own acknowledgment). Submitted actions are exactly the acknowledged ones (5d). An acknowledgment alongside a `details` request is a parse error (5e). **Not possible.**
6. **Missing preview fields becoming a default:** **Yes — F1.** Missing fields become `null`, are listed and can be acknowledged and submitted; a string-typed engine value is accepted as such. Not reachable with the engine at this revision.
7. **Consequence source manipulation:** the request text is built only from the engine's preview (`request_text(assessment)`, 7a); values smuggled in the model's `reason` or in a mimicked item line are still compared with the engine's (7b, `wrong_value`); the recorded preview answer in a replayed record is not used as a source (7d: edited and re-hashed → refused, the engine is asked again). The hire `target` string comes from the model's own action (7c, harmless). **Not possible.**
8. **Failed/withheld staffing batch leaving the operations batch submitted:** no — 8a–8e scripted and `rvmixnone` on the real engine (harness received zero batches at that point; final digests equal the no-op run's). **Not possible.**
9. **Replay certifying fabricated records:** partial edits (changed engine answers with recomputed hashes, removed attempts, reordered attempts, rewritten outcome, stopped reason, digests, pointers, budget) are all refused. A **complete, consistent** fabrication from hand-written replies is accepted (9e, 9f): **F2**.

**Other attempts:** a reply with `<think>` wrapping or a code fence carrying the acknowledgment is accepted (L10, by design); duplicate JSON keys (N4); the sensitivity mutations below.

**Sensitivity of the tests to the gate's code** (work copy mutated, then restored): ignoring the displaced count in `match()` → `test_12` FAILED and witness L7 flagged three cases (4b/4c/9e unaffected, as expected); forcing the final check to agree → `test_24` FAILED. `test_identities_pinned` passed under the first mutation (N6).

## 5. Not checked, and why

* **No live model.** The brief forbids inference; Stage B's questions (whether real models acknowledge accurately or learn to repeat the procedure) are untouched.
* **Historical live recordings in `docs/benchmark/*/…-decisions.jsonl`** were not replayed: they use seeds outside the development set allowed here (40801, 41901/41902). Historical compatibility rests on byte-identity of agents 1–5 with `v0.11.0`, their own Python suites and the five Go replay tests on development seeds.
* **A hire on the real engine** was not run (a valid `hire` needs a full two-week roster the reviewer did not want to hand-craft); covered by one recorded real answer and the scripted shape (F4).
* **Cross-platform determinism** (`test_29`) was run on linux/arm64 only; CI compares amd64/arm64/darwin.
* **Whole Go suite, `-race`, and the holdout/reserved streams:** excluded by the brief.
* **The engine's `validate`/`preview` implementation itself** (whether its reported consequences are *right*) is out of scope; the review checked that the agent reproduces what the engine reports.
* **Budget stop under wall-clock time** was exercised only through the recorded `stopped == "budget"` path and code reading (`:483-486`, `:679-681`), not by a timed run.
