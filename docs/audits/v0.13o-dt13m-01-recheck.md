- extra or missing keys;

## 4. R-PIN-001 enforcement

1. **The protocol pins the exact standard.** The pin names `dreamteam.acceptance-standard/v1` and `analysis/alternatives/acceptance_v1.json`. Its SHA-256 `c6af89ed…` equals the hash I computed. The draft differs from the V0.13m-lite draft only in `schema`, `id` and `acceptance`.
2. **The tolerance is integer 60 (type-strict).** `toleranceSeconds` is the integer 60 in the protocol and in the acceptance file, and 60 is the value the verifier applies. The recorder compares canonical JSON text (`v13o.py:82`). The verifier uses typed equality and `type(tol) is int` (`v13o_verify.py:79-80`).
3. **The tolerance does not loosen the four-hour guard.** The tolerance is read only at `v13m_verify.py:1497-1503`, inside `_wall_clock`. The guard at `v13m_verify.py:933` is `e + timeoutSeconds > wallClockSeconds`, with no tolerance. Witnesses:
   - A genuine recording at exactly the threshold does not halt and ends COMPLETE.
   - At the threshold plus 0.001 s it halts, PARTIAL.
   - That halt, with elapsedSeconds moved 0.002 s, 0.5 s, 30 s or 59 s below the threshold (all inside the 60 s timestamp tolerance), is INVALID under R-HALT-001 ("no limit fires") and refused (`scratch/s4/results.json`).
4. **The recorder refuses bad pins at every entry point.** `protocol` generates the pin. `schedule`, `check`, `run` and `run_schedule` all call `check_binding` first. With a 120 s pin, the command-line `schedule`, `check` and `run` all exit 1 with the DT13M-01 refusal. `run_schedule` refused all 9 tampered protocols (`scratch/s2`, `scratch/s4`). The unchanged V0.13m-lite `schedule` command also refuses V0.13o protocols (`scratch/s6/v13m-cli-schedule.txt`). The underlying V0.13m-lite `run_schedule` still records under any protocol (DT13O-05).
5. **The verifier enforces R-PIN-001 on its own.** It does so in `classify` (the archive is forced to INVALID) and before `analyze` (analysis is refused). It does not depend on the recorder (section 3).
6. **An altered acceptance file cannot reinterpret existing evidence.** Any byte change to the acceptance file breaks the pinned hash, including an equivalent re-serialization or one added newline. Everything is then INVALID (R-PIN-001), so the change fails closed. Only R-HALT-003's `toleranceSeconds` is consumed from the file (`v13m_verify.py:1497`). The whole file is checked by hash and by strict-parse equality. A new 120 s acceptance file plus a protocol re-pinned to it does accept +60.1 s under the ambient copies. That is a different protocol (SHA `9654f92b…`), and the repository verifier rejects it (DT13O-02).
9. **Tampered protocols are rejected.** All 9 recorded tampers and both rebound-and-resealed tampers are INVALID and refused (section 2).

## 6. Findings

- **DT13O-01 (MINOR).** The recorder and verifier disagree on acceptance files other than the committed bytes.
  - **Cause:** `v13o_verify.py:75` builds `{r["id"]: r}`, so a duplicate R-HALT-003 collapses and the last entry wins. `v13o.py:63-67` parses permissively but requires a single R-HALT-003.
  - **Witnesses:** `scratch/s3arch/repinned-dup-rule-60-then-120` (accepted by the ambient verifier, 120 s applied, while the recorder refuses) and `scratch/s3arch/repinned-dup-top-key` (recorded by the ambient recorder, rejected by the verifier). The repository verifier rejects both.
  - **Smallest fix:** in the verifier, require unique relationship ids. In the recorder, parse the acceptance file with the same strict parser, or have both sides require the pinned constant `c6af89ed…`.
  - **Model-visible content:** unchanged.
- **DT13O-02 (NOTE).** The verifier takes the pinned acceptance SHA from the protocol it is given; nothing in its code fixes that SHA. Changing both the acceptance file and the protocol, with the id still `v13o-alt-1`, therefore changes the tolerance applied (`scratch/s3arch/repinned-tol120`, accepted only under the ambient copies). Protection rests on the protocol SHA that the lock records.
  - **Fix:** the lock record and the analysis should require the locked protocol SHA. Optionally, embed `c6af89ed…` in `v13o_verify.py`.
  - **Model-visible content:** unchanged.
- **DT13O-03 (NOTE).** R-HALT-003 can only detect a discrepancy that the timestamps around the halt actually show. If UTC runs 60.1 s ahead and no timestamp was recorded after the jump and before the halt, the archive is accepted (`scratch/s1/skew-60.1`, `scratch/s1/request-skew-60.1`). With a tight bracket the same gap is rejected (`scratch/s1b`). This behavior predates V0.13o.
  - **Fix:** word the `onExcess` statement as "a discrepancy demonstrable from the bracketing timestamps".
  - **Model-visible content:** unchanged.
- **DT13O-04 (NOTE).** Both sides parse the protocol file with the permissive `json.load` (`v13o.py:105,143,146`; `v13m_verify.py:1824`). Protocol text with `"toleranceSeconds": 120` followed by `"toleranceSeconds": 60` is accepted by both, and 60 is applied. There is no reinterpretation, but a human reading the file could be misled (`scratch/s2/text-dup-key-120-then-60.json`).
  - **Fix:** parse the protocol strictly.
  - **Model-visible content:** unchanged.
- **DT13O-05 (NOTE).** The unchanged `v13m.run_schedule`/`Recorder` records under protocols that have no pin or a tampered one (`scratch/s3arch/tampered-*`). The verifier rejects all of those archives.
  - **Fix:** the live runner, when it is implemented, must enter through `v13o.run_schedule`.
  - **Model-visible content:** unchanged.

None of these is a BLOCKER or MAJOR.
