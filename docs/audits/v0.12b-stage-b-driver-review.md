### 3.1 Fidelity (area 1)

What was checked, and found as specified:

* Each draw calls `llm_agent5.ask(..., workflow="validation-first-preview")`
  or `llm_agent6.ask(...)` itself. No message text, parser, validation,
  feedback, preview, eligibility, assessment, matching, rejection text,
  final check or withholding is reimplemented; `rec["workflow"]` is added
  exactly as `llm_agent6.run` does.
* **The first request:** `PointModel.call` compares
  `json.dumps(payload).encode("utf-8")`, the bytes `ModelClient.call`
  sends, with `X.body_bytes(sourceRequest)`, the committed source
  context's request in the client's key order; it then answers with the
  recorded proposal and sends nothing. All twelve points have the proposal
  at attempt 1 (`points/manifest.json`), so the agent's two-message first
  request is the recorded one; the protocol's "failures and details
  already used before the proposal carried over" is therefore vacuous
  (nothing to carry), which is fine.
* **Settings:** `A3.load_settings` on the pinned V0.5c file; the model
  name, system prompt hash, timeout 300, `maxRetries` 1 and
  `allowDetails` checked against the protocol; temperature 0,
  `max_tokens` 4096, `json_object`, decision budget 900 s come from the
  pinned file. Nothing is overridden.
* **Decision budget:** `PointModel.spent` is `LiveModel.spent` verbatim,
  with `start` set a few lines before `ask()` as `llm_agent6.run` does.
  Arm A's budget is inside `llm_agent5.ask` (not injectable); with at most
  two 300 s calls it cannot bind; if it ever did, replay would refuse the
  draw, as `DRIVER.md` §8 says.
* **Engine reader:** `json.loads` for A, `llm_agent6.json_loads` for B,
  applied to every line of the arm's session including `Session.to_point`.
  `_Duplicated` is a `dict` subclass, so transcript comparison, logging and
  JSON output are unaffected; `assess()` re-serializes its answer as plain
  JSON exactly as the agent does.
* **Request ids:** `r1, r2, …` per draw. In an agent run they count for
  the whole run; ids never enter a prompt, a record or a comparison (the
  fidelity script compares op, args, ok, result, error).
* **ProtocolError:** `EngineHarness.request` raises
  `A3.ProtocolError(op, error)` on `ok: false`, which both agents catch
  where they catch it (`validate_all`, `assess`, `request_preview`,
  `final_check`). The driver loads one copy of each agent module and
  asserts it, so there is one `ProtocolError` class.
* **`Halt`:** neither agent has a broad `except`; `Halt` is raised inside
  `model.call`, outside both agents' `try` blocks, and propagates; the
  attempt under way is never appended. Confirmed by grep and by W2.
* **Details:** every path to a second model call closes `details_open`
  first in both agents (A5 lines 435/448, A6 lines 753/760/772), so no
  details request, and no `observe` for details, can occur after the
  proposal. The CallBound sweep's `details` kind exercises this.
* **An unencodable reply** (a lone surrogate from a `\ud800` escape):
  both agents' own `sha256(content)` raises `UnicodeEncodeError`, a
  `ValueError`, so the reply is treated as unreadable and retried; the
  record never holds the surrogate and `draws.jsonl` is written. Checked
  by execution (W2 case A).
* **Fidelity evidence:** `fidelity/fidelity.md` reports 113 of 113 cases
  faithful on the real engine and every apply check equal; the unit tests'
  `Fidelity` class runs every V0.12a scripted case and V0.11b's arm C cases
  through both the driver and the bare agent. Both pass here.

### 3.2 Initial-state equality and pooled reuse (area 2)

* **The engine:** `World.Validate`, `ValidateBatch` and `PreviewStaffing`
  run `staffBatch(..., do=false)` on the live state with `st.now` saved and
  restored; the hypothetical (`newHypo`) is a copy. The only state the
  state digest skips that these paths touch is `state.drawMemo`, a memo of
  `rng.Hash(seed, domain, keys)`: a pure function of its key (`draws.go`),
  so filling it changes no later draw. There is no sequential RNG in
  `Engine` (`engine.go`); randomness is keyed hashing. `digests` covers the
  log hash, ledger hash, action record digest and the state digest (with
  live pending events); `hello.clock.logTotal` would show any log entry.
* **W4, executed on the real engine** at `ss-qwen-s42002-p7`
  (teleradiology start) and `fl-qwen-s41902-p24` (two terminations, 6
  displaced): one pooled arm-B session; snapshot of `digests`, `hello`,
  the full observation (`recentLog` 2000), the compact observation the
  agents use, the catalog, `validate` and `preview` of the staffing batch
  and of the whole proposal; six complete arm-B draws through
  `stage_b.run_draw` with the pool (each acknowledged, final-checked and
  submitted: 13 and 11 engine requests per draw); the snapshot again; then
  a fresh session's snapshot. **Every view was identical** before and
  after the six draws and identical to the fresh session's, and the six
  draws' deterministic records were identical. Total 47 s and 79 s.
* The driver checks the digests' SHA-256 at every draw's start against the
  schedule and records them at its end; `check` reports any difference.

### 3.3 Initial proposal and request equality (area 3)

`schedule()` derives `expected` from the committed contexts (digests,
`body_bytes(sourceRequest)`, the proposal's SHA-256); `run_draw` re-checks
the proposal and request against the entry before opening the engine,
then the engine's digests against the entry. The source request's key
order is the client's (`test_source_request_keeps_the_clients_key_order`),
the Stage B contexts file's sorted copy is only compared canonically, and
`classify` compares the first attempt's actions with the proposal's by
dict equality (order-free). `check_schedule` compares the committed file's
entries with the regenerated schedule. Verified by execution (the unit
tests' `Schedule` class on the committed files). The pinned agent hashes
in `protocol.json` and the workflow and contract identities were
recomputed and match the snapshot's files.

### 3.4 Arm isolation (area 4)

One `dt agent --stdio` process per (point, arm), never shared; a separate
reader per arm; a new `FixedMemory`, `EngineHarness` and `PointModel` per
draw; the settings dict is read by both agents and mutated by neither
(`prompt_settings` and `retryBudget` copy); the transport is the stateless
`ModelClient.call`. The only shared resource is the model server (its
cache), an accepted assumption of shared-prefix/v4.

### 3.5 Ordering and `check_rows` (area 5)

`check_rows` compares each recorded row's (seq, model, point, arm, draw,
expected) with the schedule's entry at the same position and refuses more
rows than scheduled; a missing, duplicated, unlisted, reordered or
wrong-arm row therefore fails, and so does a wrong expected start (tests
18–22; also re-run here). Only the last row may be unfinished. See D11.

### 3.6 Retry and call accounting (area 6)

The bound of **2 model calls per draw** after the recorded proposal was
checked by hand on both loops: the first transport call is always made
with `failures` 0 (after a request, preview or resend) or 1 (after a
refusal's feedback); the only ways to a third transport call would be a
second retry (`failures` 2, excluded by `maxRetries` 1), a details reply
(excluded, §3.1) or an acknowledgment request after a revision that
answered a request (B charges that revision one retry, lines 721–728). The
CallBound sweep (9 reply kinds, 3 deep, 5 starts) finds 2 as the maximum.
Failed calls (timeouts, HTTP errors) are counted toward both limits before
the next call. The limit of 4 is a guard that cannot bind.

### 3.7 Limits (area 7)

`Limits.before_call` (per draw, run, wall clock with the whole 300 s
timeout) and `before_draw` (wall clock) are as `DRIVER.md` §3 says; tests
15–17 and W2 case D confirm them. See D8 for engine time.

### 3.8 Partial runs (area 8)

Executed here: the wall-clock stop (test 17 and W2-D: `interrupted` row,
`run.json` PARTIAL with the stop), the call budget, five transport
failures, an unhealthy server before the run, a driver failure (W2-B), the
operator (W2-C), and the refusal to run into a directory with `live/`.
`run.json` is written in a `finally` on every path, including the health
stop before any draw; `draws.jsonl` is flushed per draw. `analyze` on a
PARTIAL run gives `BminusA: null` and `pooled: null`, Wilson intervals on
the observed count only, and the tables open with the status, coverage and
stop (the committed mock run shows exactly this: 44 of 420, draw 45
interrupted, `wall_clock`). An interrupted draw is replayed with its
recorded halt at the same call and not classified. There is no resume
command, and `run` refuses an existing `live/`. Gaps: D6, D7, D11.

### 3.9 Classification (area 9)

Every class in PROTOCOL.md §5 was reproduced on the scripted engines
(tests 01–14 and W1): A proceeded, B revised with and without an accurate
acknowledgment first, C abandoned, D withheld for wrong value, malformed
entry, stale token, missing acknowledgment, retries spent, unreadable
replies, timeouts and unavailable consequences, E not required for a
non-qualifying proposal and for a refused proposal not corrected, and A's
four preview classes. A state change during the preview is caught by the
agent (`consequences_unavailable`, D). The defects found are in the
definitions' boundaries: D1 to D4.

### 3.10 Replay (area 10)

`replay_draw` serves each recorded response only to the request with the
recorded SHA-256 and only if its body still has its SHA-256, requires
every recorded response to be used, re-raises a recorded halt at the same
call, and compares `deterministic()` of the re-run with the record:
schedule entry, status, halt, both digests, the agent's whole decision
record, the batches, every engine request and answer, and each call's
request hash, status, error and response hash. Tampering with a body, the
record, an engine answer or the number of calls is refused (test 23, W3
case 2). Nothing nondeterministic was found in the deterministic set: the
record's `time`/`day` are the engine's clock; latencies and send times are
kept out. See D5 for the fields replay leaves unverified.

### 3.11 Financial evidence (area 11)

`continuation` is shared-prefix/v2's `decision_evidence` unchanged
(validate, apply only if every batch is valid, the no-action suffix) plus
the engine's own previews of the staffing batches at the recorded state.
`exposure()` copies `commitmentCents`, `creditSupported`, `directExposure`,
`reversibility` and `affordability` from financial evidence v1's summary,
and takes severance, retained-obligation lines and the displacement count
from the previews' own fields. Nothing is computed from outcomes; the
`creditSupported`/affordability statuses are FE v1's rules, declared
unchanged by the owner. The fidelity run's apply check (the agent's own
harness against the continuation, per point) was equal at every point.

## 4. Findings

Severity: **Blocker** (must be fixed before the lock), **Major**, **Minor**,
**Note**. "Executed" says whether the witness was run by the reviewer.

### D1 — "Unchanged" is defined two ways: the outcome and the class disagree on a reordered resubmission — **Major**

* **Witness (executed, W1 cases 1 and 1b):** arm B on the scripted
  engine, proposal `[FIRE, FIRE2]`; reply 1 `[FIRE2, FIRE]` with the
  acknowledgment of the first request; reply 2 `[FIRE2, FIRE]` with the
  acknowledgment of the second request. Result:
  `outcome: kept, class: B_revised, accurateBeforeChange: True,
  submitted: True`. Arm A, proposal `[STAFF, OPS]`, review reply
  `[OPS, STAFF]`: `outcome: kept, preview.class: revised`.
* **Evidence:** `classify` takes the outcome from `llm_agent4.response_of`
  (`same_actions`: sorted compact JSON, order-free), but `ack_class` and
  `preview_class` use `llm_agent6.same` (list order matters). llm-agent 6
  itself treats a reordered reply as a new proposal (new payload token,
  new request, one retry charged), so `B_revised` follows the agent; the
  outcome rule says `kept`. PROTOCOL.md §5 defines A as "R was submitted
  unchanged" and "kept" "by canonical content" without saying they differ.
  Two of the twelve points have multi-action proposals
  (`ss-qwen-s42001-p20`, `fl-qwen-s41902-p24`), and a sampled model
  reordering a list is plausible, so the central B-vs-A table could count
  a `kept` draw as `B_revised`.
* **Fix:** choose one rule and state it in §5. Either make the class use
  `same_actions` for "unchanged" (then a reordered resubmission is A
  proceeded, with the extra request visible in `modelCalls`), or keep the
  agent's exact-order rule and say so in §5, adding a per-draw flag
  (`reorderedOnly`) so that `kept` with `B_revised` is explained in the
  tables. The same choice applies to A's preview classes.

### D2 — `lastProposalValid` is false when the last proposal was valid but its acknowledgment was rejected — **Minor**

* **Witness (executed, W1 case 2):** arm B, proposal `[FIRE]` (valid,
  qualifying), two replies with the same actions and a wrong
  `severanceCents`. Result: `class: D_withheld`, `outcome: withheld`,
  `lastProposalValid: False`, although attempt 1's validation was accepted
  and the proposal never changed. Attempts 2 and 3 have `validation: None`
  because the agent raises before the final check.
* **Evidence:** `classify` takes `lp` as the last parsed proposal and
  requires `lp["validation"]`; an acknowledgment reply is only validated
  (by the final check) when the match is accepted.
* **Fix:** define "the final proposal's validity" from the last attempt
  that carried a validation of the same actions (or from the pending
  proposal's validation), and say so in §5.

### D3 — "Accurate before a change" is matched against the request the reply answered, not against R — **Minor**

* **Witness (executed, W1 case 3):** arm B, proposal `[FIRE, FIRE2]` (R);
  reply 1 `[FIRE]` with an acknowledgment of R carrying a wrong
  `noticeDays`; reply 2 `[]` with an accurate acknowledgment of the
  revision's request. Result: `class: C_abandoned,
  accurateBeforeChange: True`; the acknowledgment entries are
  `(accurate False)` for R and `(accurate True)` for the revision.
* **Evidence:** PROTOCOL.md §5 says B and C record "whether a reply that
  changed the actions had first stated **R's** consequences exactly";
  `ack_entries` matches each acknowledgment against the last qualifying
  request before it. With `maxRetries` 1 the two definitions differ only
  in this sequence (two changes, the second acknowledging the first
  revision), which the retry budget allows.
* **Fix:** align the wording with the code (the code's reading, "the
  request it answered", is the one llm-agent 6 matches) or restrict the
  flag to acknowledgments of R; either is a one-line change.

### D4 — Class D with no withheld reason: a revision in answer to the request is refused and the retries are spent — **Minor**

* **Witness (executed, W1 case 4):** arm B, scripted engine refusing
  every validation after the first (`final="notice_too_short",
  final_after=1`); proposal `[FIRE]` (qualifying, request shown); reply 1
  `[FIRE2]` (refused); reply 2 `[FIRE2]` (refused). Result:
  `outcome: refused, class: D_withheld, acknowledgment.withheld: None,
  stopped: None`.
* **Evidence:** `ack_class` returns D whenever acknowledgment was required
  and nothing was submitted; the agent clears `pending` on a revision, so
  it records no `withheld` and no `stopped`. PROTOCOL.md §5's D lists
  `acknowledgment_not_accepted`, `final_check_disagrees`,
  `consequences_unavailable`, an unreadable reply or a failed request; not
  this case. The B table's "Withheld" column (a count of `withheld`
  reasons) will not show it, so a D count can exceed the withheld reasons.
* **Fix:** add the case to D's definition ("a revision answering the
  request was refused and no retry was left"), and record a reason for it
  in `classify` (e.g. `revision_refused`), or report `outcome` next to the
  class in the B table.

### D5 — Replay does not verify the body-derived live metadata — **Minor**

* **Witness (executed, W3 case 1):** in a recorded draw, change
  `calls[0].servedModel` to another name, or `usage`, or `finishReason`:
  `replay_draw` accepts the row and `deterministic()` is equal. Changing
  one byte of `body` is refused (hash).
* **Evidence:** `servedModel`, `usage` and `finishReason` are read from
  the body at run time (`RR.response_fields`) but stored beside it;
  `deterministic()` keeps only n, request hash, status, error and response
  hash, and replay does not recompute the three from the (verified) body.
  `inference.json` and the token totals in the tables are built from
  them, and `servedModel` is the record's only statement of which model
  answered.
* **Fix:** in `replay_draw`, recompute the three from `c["body"]` and
  compare (they are deterministic given the body), or put them in
  `deterministic()`.

### D6 — A model call that raises an exception the client does not catch is lost: no request record, `modelCalls` not counted — **Minor**

* **Witness (executed, W2 case B):** a transport raising
  `http.client.IncompleteRead` on the first call. Result: the run stops as
  `driver` ("draw 2: IncompleteRead"), `run.json` PARTIAL with
  `drawFailed: 2`, `modelCalls: 0`, and no record of the request anywhere.
* **Evidence:** `ModelClient.call` catches `HTTPError`, timeouts,
  `URLError` and `OSError`; `http.client.HTTPException` (`IncompleteRead`,
  `BadStatusLine`; `RemoteDisconnected` is an `OSError` and is caught)
  escapes; `PointModel.call` increments `limits.calls` and appends to
  `calls` only after the transport returns; `run_draw` discards `out` on
  an exception. PROTOCOL.md §4: "every request is recorded". The agent
  itself would crash on the same exception, so fidelity is not at issue;
  the loss of the record is.
* **Fix:** in `PointModel.call`, wrap the transport: on an unexpected
  exception, append the call with `status None` and
  `error "client: <type>: <message>"`, count it, and re-raise; and in
  `run`, write the aborted draw's partial record (its calls and engine
  log so far) to `live/aborted-draw.json` before stopping.

### D7 — Ctrl-C during a draw: the draw's completed calls are counted in `run.json` but recorded nowhere — **Minor**

* **Witness (executed, W2 case C):** a transport raising
  `KeyboardInterrupt` on the second call of a draw. Result: `run.json`
  PARTIAL, `stopped: operator`, `modelCalls: 1`, `drawsCompleted: 1`,
  while the recorded rows hold 0 calls.
* **Evidence:** `run()` catches `KeyboardInterrupt` outside the per-draw
  `try`; the in-progress draw's `out` (with its `calls`) is discarded.
  PROCEDURE.md §5 names Ctrl-C as the way to stop a run that looks wrong.
* **Fix:** as for D6: write the aborted draw's partial record on the way
  out, and let `run.json` name it (`drawAborted`), so that `modelCalls`
  equals the recorded calls.

### D8 — The wall-clock stop bounds model requests, not engine time — **Note**

* **Witness (executed, W2 case D):** scripted clock, 100 s per engine
  request, 290 s per model request, `wallClockSeconds` 1200. The run
  stopped at 1,600 s elapsed and ended at 1,700 s.
* **Evidence:** `before_draw` and `before_call` test
  `elapsed + 300 <= wall`; the session opening (5–36 s on the Pi) and the
  draw's engine requests after the last model call are not bounded. On the
  Pi the overrun is at most about a minute. PROTOCOL.md §4 and DRIVER.md
  §3 say "the run cannot overrun"; it cannot overrun **by a model
  request**.
* **Fix:** wording only, or test the wall clock once more after the
  session is opened.

### D9 — The lock's contents and the schedule/protocol hash circularity are not settled — **Minor** (to settle in the lock commit)

* **Evidence (code and documents; `check_lock` and `check_schedule`
  read):**
  1. PROTOCOL.md §8 lists what `lock.files` pins: the driver, its
     fidelity code and tests, the four agents, the selection, the points,
     the schedule, the settings files and the documents. The driver also
     executes through `analysis/repeatability/decision_experiment.py`
     (`Session`, `decision_evidence`, `server_signature`),
     `workflow_experiment.py`, `feedback_experiment.py`,
     `prompt_sample.py` (`recording_point`), `repeat_run.py`
     (`server_state`, `response_fields`),
     `analysis/evidence/financial_evidence.py`,
     `analysis/acknowledgment/scripted_cases.py`, and the test fixtures
     `test_llm_agent4/5/6.py` and `test_workflow_experiment.py`; and
     `load_protocol` rebuilds the selection from
     `docs/benchmark/v10b-dev|v10c-dev|v11b-dev/points/contexts.jsonl`,
     `v10c-dev/points/inventory.json`, `v11b-dev/points/manifest.json` and
     the twelve recordings' `decisions.jsonl`. None of these is named.
  2. `schedule.json` embeds `protocolSha256`; the lock changes
     `protocol.json`, so the committed `schedule.json` would name the
     pre-lock protocol; and pinning `schedule.json`'s file hash inside
     `protocol.json` is circular. The code already provides
     `lock.scheduleEntriesSha256` (the entries' canonical hash), which is
     not circular; §8 should say that is the pin and that `schedule.json`
     is regenerated in the lock commit. `check_schedule` does not verify
     `schedule.json`'s `schema` or `protocolSha256`.
  3. The committed mock run's `run.json` and `decisions.json` embed
     `protocolSha256`, and `analyze` requires it to equal the protocol's;
     after the lock, CI's regeneration of `fidelity/mock-run/` will differ
     from the committed one unless it is regenerated in the lock commit
     (about 18 minutes on the Pi), together with `README.md`'s hash table.
  4. The run is from a clean checkout of the locked commit, which pins
     everything above by content; the gap is in what `check` and `run`
     verify on the machine, not in reproducibility.
* **Fix:** enumerate `lock.files` to include the modules and inputs in
  (1); pin the schedule by `scheduleEntriesSha256`; have `check_schedule`
  check `schema` and `protocolSha256`; and state in §8 the regeneration
  order of the lock commit (write the lock → `schedule` → `mockrun` →
  README hashes → CI green).

### D10 — `check` exits 0 when the lock does not hold — **Minor**

* **Witness (code; executed on the unlocked protocol, §7):**
  `main()` returns `1 if bad else 0`, where `bad` is the point-arm starts
  whose state changed; the lock problems are only printed. On the
  snapshot, `check` prints `lock: the protocol is not locked` and exits 0.
* **Evidence:** PROCEDURE.md §1 says `check` must report `lock: holds`;
  an operator script keyed on the exit code would not see a broken lock.
  `run` enforces the lock itself, so the run is protected.
* **Fix:** `return 1 if bad or problems else 0`.

### D11 — `analyze` does not cross-check `run.json`'s `drawInterrupted` and `stopped` with the rows — **Note**

* **Witness (W3 cases 3–4, code):** `analyze` checks
  `run_doc["drawsCompleted"] == len(completed)` and the status is
  COMPLETE or PARTIAL; it does not check that `drawInterrupted` names the
  last row when that row is `interrupted`, nor that PARTIAL implies a
  stop or a shortfall. The analysis copies `drawInterrupted` and
  `stopped` from `run.json`.
* **Fix:** two assertions in `analyze`.

### D12 — `EngineHarness.request` omits the `protocol` field check of `llm_agent3.Harness.request` — **Note**

* **Evidence:** the agent's harness raises `ExchangeError` if an answer's
  `protocol` is not `AGENT_PROTOCOL`; the driver's checks the id only.
  With the real engine every answer carries the protocol, so this cannot
  change an outcome.
* **Fix:** optional one-line check, for symmetry.

### D13 — Two record fields differ from a mid-trajectory agent record, by construction — **Note**

* **Evidence:** `previousExecution` is `None` in every Stage B record
  (`prev=None`), where an agent at the same point of its own run would
  record the previous point's execution; and request ids restart at `r1`
  per draw. Neither enters a prompt, a message, a comparison or a
  classification; the prompt is checked byte for byte against the
  recorded request. DRIVER.md §8 could say so under "known limitations".

## 5. What the reviewer could not check

* **Live behaviour:** no model was contacted; the live transport
  (`ModelClient.call`), the server checks (`RR.server_state`) and the
  real latencies ran only in scripted form. The driver's handling of a
  live reply kind not covered by the scripted cases rests on the agents'
  own code, as DRIVER.md §8 says.
* **The full fidelity and mock runs** were not re-executed here (45 and 18
  minutes); the committed outputs were read and their generating code
  reviewed, and their session pattern was exercised at two points (W4).
* **CI's cross-platform comparison** was not reproduced.
* **The model server's cache** as a channel between arms and draws is an
  accepted assumption of shared-prefix/v4 and was not examined.

## 6. Final verdict

**GO for locking the protocol**, on these conditions:

1. **Before the lock commit** (each changes a file the lock pins, and a
   change after the lock is an amendment): decide and document D1 (one
   rule for "unchanged", or the flag), D2 and D4 (the two definitions),
   and D3 (the wording); settle D9 (the lock's file list, the schedule
   pin, and the regeneration order) and D10 (the exit code). None needs
   more than a few lines of code and of §5/§8.
2. **Before or after the lock, at the owner's choice:** D5 to D8 and D11
   to D13 may be fixed in the same commit or recorded as known
   limitations in DRIVER.md §8; none can change which draws are
   recorded, replayed or counted, except D6/D7, which lose only the
   record of an aborted draw's calls.

No finding touches fidelity, initial-state equality, arm isolation, the
limits as designed, the partial-run procedure on its designed paths, or
replay's ability to refuse a changed body, record or engine answer. This
review does not authorize live inference.
