## Not fixed: needs an owner decision

**F1, the rest (BLOCKER for lock, owner decision D7).**
* The reviewer showed that a valid free-text field carries any text into
  every turn: an action's `requestId`, or an employee's name in a
  scenario. That includes an evaluation-only value written in words.
* No lexical check can tell what a string means. The structural guard
  holds only for what the engine itself adds.
* **The options:**
  * accept a trusted-input threat model: inputs are recordings
    (written by a model that never saw an evaluation value, bound by
    SHA-256), committed and pinned files, or the model's own live reply;
  * or constrain or replace the displayed free-text fields with neutral
    identifiers. That would change the presentation, with a new pin and
    a new human review.
* The documents now state the threat model and no longer claim more
  (`EXPERIMENTAL_DESIGN.md` §3; `LIMITATIONS.md`; `PRESENTATION_REVIEW.md`
  P9).
* The protocol cannot be locked before D7.

**F7 (owner decision D8, with the human review).**
* Only the control text says "Nothing has been applied yet".
* Aligning the texts changes a pinned template's identity.
* The design no longer claims identical framing (§2, §7), and the
  difference is P8 in the review package.

**N1.** Each of the reviewer's policy points is now an owner decision in
`EXPERIMENTAL_DESIGN.md` §8:
* **The estimand:** sensitivity to a named pair of contexts with its
  co-differences, not to one fact. Stated in §6.
* **The operations batch** when the decision is abandon or no action
  (D9).
* **The shared outcomes (D10):**
  * departure includes failures, which are reported separately;
  * "submitted a different batch" is used in place of the arm-dependent
    `revised`.
* **The outstanding lock gates:** the human review, D1–D10, and V0.13d's
  workflow, driver and generator.
