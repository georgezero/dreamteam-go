# DreamTeam V0.13c independent technical review

**Verdict: do not lock the protocol yet.** The narrow F4 remediation is sound, historical v1 evidence is unchanged, and the committed alternatives, branch, compatibility, sensitivity and replay-backed inventory tests pass. Nevertheless, the claimed text information boundary is bypassable through valid action and scenario fields; the sensitivity ledger does not describe all visible differences; and the implemented turn trigger does not enforce acceptance of the whole proposal. These are one BLOCKER and two MAJOR findings. Six MINOR findings concern decoding, identity checks, transcript verification, arm wording, control classification and inconsistent budget documentation. This review covers the supplied export of `e8470c0`; the snapshot passed all 1,836 manifest entries before and after review. Only a new witness test file was added to source in `work/`; no production code or committed evidence was changed. No inference endpoint or API key was accessed. The required human presentation review and owner decisions remain outstanding independently of these technical findings.

## 1. F4 deduplication

**No defect found in the requested repair.** `selection.go:204` traverses the already limited v1 list, keys each canonical action batch, keeps the first and records later equal batches. It does not refill, modify validation, substitute actions or reorder survivors. Candidate labels, IDs and sources are not part of the batch key. Empty proposals do not qualify, so an applying selection cannot remove the second-position empty `no_action` as a duplicate of the proposal.

Adversarial cases exercised by the committed tests:

- `[terminate E04 Oct 27, terminate E04 Oct 27]`: v1 has four candidates; v2 has `proposal, no_action, without_1`, with `without_2=without_1` recorded. The proposal remains refused.
- `[terminate E03 Oct 27, terminate E03 Oct 27, terminate E04 Oct 27]`: v2 removes `without_2`; it does not introduce `without_3`.
- Eighty two/three-termination proposals and longer batches check subset preservation and the four-candidate limit.
- Different labels with equal batches collapse; different last days remain distinct. Nil versus empty nested action values are canonicalized consistently.
- `[terminate E04, worklist, terminate E04]` keeps both reordered leave-one-out batches. Empty-batch and stable-order/identity cases pass.

Relevant output:

```text

--- PASS: TestSelectionV2DuplicateLeaveOneOut
--- PASS: TestSelectionV2LabelsNotCompared
--- PASS: TestSelectionV2ActionOrder
--- PASS: TestSelectionV2DifferentValues
--- PASS: TestSelectionV2NoAction

```

`session.checkAlternatives` and `batchKey` use the same JSON round-trip canonicalization and preserve action order. Treating reordered batches as distinct is sound for this contract: the engine processes ordered batches and refusal positions can differ. It is deliberately not a test for semantic equivalence of eventual states. Changing that policy would require another rule version; no such change is needed for F4.

## 3. Candidate identities

Generated identities are stable, distinct within a selection and rule-specific: SHA-256 over the rule name, candidate ID and canonical actions. The unchanged human-facing IDs need not themselves contain the rule name. `VerifySelection` rebuilds under the named rule, checks its pin and compares all fields, including removals. The existing tests reject wrong pins, reordered/edited selections and reintroduced duplicate v2 batches; both v1 and v2 comparisons pass `DecodeAgentAt` when genuine.

**F3 — structural candidate-hash check missing.** At `comparison.go:586`, `CandidateSha256` is checked only for nonemptiness. `TestAuditDecoderChecks` changes the proposal's candidate hash to `"forged"`, recomputes the outer comparison digest and encodes it:

```text
forged candidate identity structurally accepted; bound decoder refuses:
comparison does not satisfy dreamteam.management-alternatives/v1:
the comparison does not rebuild
```

The candidate hash can be verified from the decoded rule, ID and actions; this does not need engine access. Add that check. This is a structural-contract weakness, not a bypass of `Steps`: `VerifyAgent` correctly rejects it.

**F4 — malformed JSON accepted by the bound decoder.** `DecodeAgent` uses `dec.More()` as an end-of-input check (`comparison.go:649`). `More` answers whether the current array/object has another element; a closing delimiter makes it false. Append any of these suffixes to an otherwise genuine encoded comparison:

```text
DecodeAgentAt accepts invalid JSON suffix "]"; json.Valid=false
DecodeAgentAt accepts invalid JSON suffix "}"; json.Valid=false
DecodeAgentAt accepts invalid JSON suffix "] garbage"; json.Valid=false
```

The witness calls the real bound decoder against the original session/selection. A second decode must return `io.EOF`; trailing syntax, another value or garbage must fail. The accepted comparison contents remain genuine, so this is not future-information injection, but it violates strict decoding and allows different consumers to disagree about the same input.

## 4. Audience separation

The ordinary typed path is well separated. `Steps` calls `SelectV2`, `BuildAgent`, `Encode`, `DecodeAgentAt`, then the fixed `Summary`/`Detail` templates. It does not build an evaluation or branch. Metadata such as comparison hashes stays outside `Message` and `Inspect`. Existing tests reject unknown projection fields, class B values and non-decision-point sources, and reject disguised value edits at the engine-binding stage. The unmodified evidence and all 20 inventory points build successfully without exposing their evaluation records.

**F1 breaks the stronger claimed boundary.** A type with arbitrary strings is not incapable of carrying an evaluation value. Binding the comparison to the session proves that it reflects that session and proposal; it does not prove that names or action identifiers contain only permitted information. The text guard is lexical, and `hexRun` recognizes lowercase hex only. Section 11 supplies successful end-to-end witnesses through `Steps`, including an actual branch-derived value. These do not bypass binding or edit the templates.

No spontaneous read of hidden simulator state by `BuildAgent` was found. The demonstrated threat is an upstream field already contaminated with prohibited information. The documents currently claim to prevent that too (“what it can never see” and “no run of 16 or more hexadecimal characters”), without stating a trusted-input exception.

## 5. Branch replay

**The v2 branch repair works.** `TestSelectionV2DuplicateTermination` demonstrates that the v1 duplicate comparison fails with `session.ErrBranchInput`, while v2 builds three branches and passes `VerifyEvaluation`. Historical branch tampering, common-horizon, replay, source-preservation and old-rule tests also pass.

All four requested V0.8c/V0.9c replay suites completed. Running the inventory with `DREAMTEAM_V13C_REPLAYS=$PWD` produced:

```text
=== RUN   TestInventoryV13c
--- PASS: TestInventoryV13c (149.75s)
PASS
```

Thus the committed inventory and selected manifest reproduce byte for byte; no evidence-write environment variable was set. The new CI step enables this otherwise skipped test and uses `set -euo pipefail`, so the `tail` pipeline does not mask a failing test. Copying the committed JSON afterwards is acceptable because the test has just compared regenerated bytes against it.

**F5 — `atPoint` is state-equivalent, but not verification-equivalent, to `to_point`.** Go returns immediately at the matching digest (`inventory_test.go:424`). Python continues feeding the immediately following `observe` and `actions` requests, compares their answers and returns the observation/catalog. These requests are read-only, so stopping early does not itself change the state used for the comparison. It does skip the target context's checks.

`TestAuditAtPointSkipsTail` constructs a mini/52 transcript ending in a correct digest response followed by an observation response replaced with `"CORRUPTED"`. Output:

```text
atPoint accepts corrupt observe response immediately after matching digests;
Python to_point feeds and compares it
```

The companion Python witness executes the repository's actual `Session` class against the equivalent answer sequence:

```text
ExperimentError: audit-tail: recorded request 2 (observe) answered differently
```

Extend Go's replay through those read-only target-point requests, or narrow the claim to state reconstruction and separately verify the prompt context. No corrupt committed context was found.

## 6. Template fidelity

**No invented numeric value found in the unmodified turns.** The pinned template renders action JSON, validation, descriptions, field values, timing, bases, derivations and structural counts from the comparison. Money formatting converts integer cents; headings and instructions are fixed text. `TestPresentationFidelity`, `TestArmsTermination`, both historical evidence tests and `TestEvidenceSensitivityPairs` pass. Every treatment inspect answer is rendered from the comparison that `DecodeAgentAt` rebuilt.

The control template contains the proposal, decision time and an accepted-validation statement justified by the staffing-only due check; it contains no alternative ID list, alternative consequences or comparison values. The complete-proposal qualification caveat is F6. Attacker-supplied action text can still carry prohibited content into control, as F1 demonstrates.

The unchanged presentation has known semantic limitations: derived zeros appear under “engine facts,” reversibility includes package-authored rules, severance is printed twice, and item keys/citation grammar are absent. These are disclosed in the prior review and current presentation package. They need presentation/measurement decisions, not a claim that the rendered figures are fabricated. F2 concerns the separate difference ledger, not the fidelity of the renderer itself.

## 7. Sensitivity-pair construction

The six committed pairs are real mini/52 engine states reached by no-action advancement, with scripted proposals. Both arms' turns and the evidence JSON reproduce. The facts checked include S1 displacement 0/18; S2 displacement 0/1; S3 severance $4,500/$4,345; S4 presence/absence of `adjusted`; S5 retainer $3,083.34/$1,491.94; and S6 capacity 2,481/362. The scripted policies respond to their designated inputs. There is no evidence that those numbers were typed into the renderer by hand.

**F2 — the exhaustive visible-difference claim is false.** `visible()` (`v13c_evidence_test.go:136`) retains each value's label, formatted value and `When`, but not its `Basis` or `Derivation`. It also omits alternative descriptions and the decision timestamp, and converts ordered lists to a map. Conversely, it serializes complete validation results even though accepted-action messages are not displayed.

`TestAuditVisibleOmissions` starts with a genuine comparison and independently edits description, basis, derivation, timestamp, and fact order. It recomputes the comparison digest and, when necessary, the compared table. Output:

```text
description edit: visible() identical, rendered turn different
basis edit: visible() identical, rendered turn different
derivation edit: visible() identical, rendered turn different
time edit: visible() identical, rendered turn different
order edit: visible() identical, rendered turn different
accepted validation Message edit: visible() differs, rendered detail identical
```

These edited comparisons are witnesses against the ledger; they are not claimed to pass engine rebinding. A concrete omission already exists in the genuine S3 pair:

```text
S3 basis omitted:
"two contracted weeks (40 h) at the base rate with benefits; independent of the roster"
versus
"two contracted weeks (39.5 h) at the base rate with benefits; independent of the roster"
```

The prose notes contracted-minute differences elsewhere, but the advertised exhaustive per-item ledger still drops these displayed basis strings. S1's different treatment timestamp is likewise absent from this ledger, although its control timestamp difference is recorded.

Build the ledger from the same presentation representation as the renderer, preserving all displayed fields and order. Include exact rendered diffs as a completeness check, and regenerate counts and descriptions. **Code fix required before lock.**

**N1 — owner policy:** no pair isolates one fact; the repository acknowledges this. Difference-in-differences does not mathematically remove the effects of other changed attributes or their interactions with treatment. Approve an estimand described as sensitivity to the specified pair of contexts, with named co-differences, rather than causal sensitivity to one fact alone.

## 8. Experimental-arm isolation

Both arms use one internal due calculation and agree on every tested return. Extra alternative choices, inspect availability, call count, message length, alternative counts and the two ways of choosing no action remain differences between the arms. Most are documented. The design measures the effect of that package of presentation and interaction choices; it does not isolate numerical comparison content alone.

**F6 — whole-proposal validation is not enforced.** The design says the turn is due only when the engine accepts the whole proposal. The inventory separately validates operations and staffing but calls `Steps(s, prop)` with staffing alone, then takes `StepDue` without combining it with `r.Valid` (`inventory_test.go:267–284`). `Steps` has no separate operations-validation input.

`TestAuditWholeProposalDue` uses mini/52 at the standard decision time and this reply:

```json
[
  {"type":"set_worklist_policy","policy":"not-a-policy"},
  {"type":"terminate","employee":"E04","lastDay":"2026-10-27"}
]
```

It invokes the real split/validation/inventory path with recorded validation `refused`:

```text
operations validation=unknown_policy; staffing-only Steps due=true/true;
whole-proposal Steps due=false/false
inventoryRow: valid=false stepDue=true category=termination_keep
```

Passing the mixed batch directly is not the solution: the engine forbids mixing operations and staffing in one batch. Implement the documented predicate over separately validated batches, and use that same predicate for the inventory and future driver. Current historical outputs do not change—the committed pool does not expose this combination—but corrected prospective replies can. **Code fix required before lock.**

**F7 — mismatched framing.** The same witness reports:

```text
unapplied framing: control=true treatment=false
```

Only `control-v1.tmpl:5` says “Nothing has been applied yet.” Neither the treatment summary nor detail does. `EXPERIMENTAL_DESIGN.md` §2 explicitly claims both have that framing. Align the texts or acknowledge and approve the difference. A changed pinned template needs a new identity/pin and presentation review. **Owner decision on wording/control policy, then a text fix.**

**N1 — operations scope needs an owner decision.** The design carries operations unchanged but calls `abandoned`/`selected_no_action` “nothing submitted.” Specify whether abandoning staffing also suppresses operations, and whether the shared outcome measures staffing submission or all action submission. The current package cannot settle this because its comparisons/classifiers receive only staffing.

## 9. Prospective selection

For the fixed 20-row pool, `dreamteam-v13c-select/1` is deterministic and applied as documented: category precedence, SHA-256 ordering within category, at most two points per recording, one not-due control per category, and at most one refused qualifying point per model. It reads the original recorded proposal and engine-derived metadata; it does not read later experimental revisions, selections or response outcomes to choose favorable points. All points have prior exposure, which is disclosed; this is not an unseen holdout sample.

`TestAuditSelectionPermutation` rotates the input through all 20 positions:

```text
all 20 rotations identical: selected=9
unavailable=[termination_keep valid_expensive_not_due]
```

The replay-backed inventory verifies those inputs. The only accepted historical termination displaces six bookings. The $44,687.30 valid, not-due proposal is classified as credit-supported first; the other two eligible not-due proposals have $9,863.02 stakes. Thus the unavailable categories are correct under the stated first-match rules, not evidence that no expensive valid proposal exists. There is no valid historical hire or due credit-supported point. F6 is a latent category defect outside this fixed pool.

**F9 — conflicting approval quantities.** A direct recomputation from the machine-readable protocol gives:

```text
Protocol units=21 derived draws=964 JSON draws=964 calls=4820
```

`PROTOCOL_DRAFT.md` §5 agrees. But `EXPERIMENTAL_DESIGN.md:245`, the D3 owner-decision row, still specifies **1,040 draws and 5,200 calls**. Update D3 and generate/check these derived totals from one source. **Owner must approve the final budget, not two conflicting versions.**

The protocol JSON is explicitly hand-prepared and its lock generator is deferred. Its present unit/draw arithmetic checks out; this review does not substitute for the missing generator and driver.

## 10. Outcome classification

Ordinary reply handling agrees with the specified result rules. `TestAuditClassifiers` checks both implementations against the same engine validator:

```text
reply=null: control=no_decision treatment=no_decision departure=true noAction=false submitted=0/0
reply=abandon: control=abandoned treatment=abandoned departure=true noAction=true submitted=0/0
reply=select:proposal: control=retained treatment=retained departure=false noAction=false submitted=1/1
reply=revise to Nov 10: control=revised treatment=selected departure=true noAction=false submitted=1/1
reply=empty revise: control=no_decision treatment=no_decision submitted=0/0
reply=select plus actions: control=no_decision treatment=no_decision submitted=0/0
```

Existing tests also cover unknown IDs, refused revisions and wrong-arm/not-due control steps. There is no default to the proposal for a missing, contradictory or unknown reply. `no_action` selection submits nothing; it is an explicit choice, not a fallback.

**F8 — control result is not bound to what was shown.** After building a genuine control step for E04, the witness passes a valid E03 termination as `ClassifyControl`'s separate proposal argument and supplies `select:proposal`:

```text
control text names E04; classifier given E03 returns retained and submits E03
```

The revalidator checks legality of E03, not consistency with the displayed proposal. Bind the control step to its canonical proposal and verify that binding during classification, or accept a single validated object containing both. This is an integration hazard in the exported API; no existing live-driver occurrence is claimed because that driver does not yet exist. The caller already has to use genuine, verified treatment comparisons too.

**N1 — owner policy, not a silent code correction:** `departure = result != retained` includes invalid/no-decision replies. Thus a parsing failure counts as departure even when no deliberate change was expressed. `NoActionSubmitted` intentionally excludes those failures, despite their empty submitted batch: it means choosing no action. Also, identical non-original batches can be `revised` in control and `selected` in treatment, as the Nov 10 witness shows. Departure/no-action are comparable under their stated definitions; raw `revised` is not an arm-neutral behavior count. Approve those interpretations explicitly and report failures separately. Resolve the mixed-operations ambiguity from section 8 before assigning whole-reply outcomes.

## 11. Information leakage

**F1 — successful bound-message witnesses.** `TestAuditBoundaryCarriers` uses a valid teleradiology start: plan `standard-v1`, scope `all`, effective `2026-10-27`, window `weeknights`, at mini/52 on Oct 13. Only `requestId` changes. The engine permits 1–128 characters. Output:

```text
requestId="1250D645B013BC5725FE12F089FAEF933DC7ECEB44A10A15F558A5CDCD7F284C"
accepted; control, treatment and inspect all contain it
requestId="rng=52" accepted; control, treatment and inspect all contain it
```

The first payload is the actual current state digest, uppercased. `checkText` tests `[0-9a-f]{16,}` before its word-check lowercasing, so this passes unchanged. The second encodes the actual allowed test seed without the banned word `seed`.

The same test loads the real mini scenario, changes E04's employee name using `session.FromFile`, and advances normally. These names reach the engine-bound proposal inspect answer:

```text
employee name="45DDB600C4D9675B8A901893276EAEC37F33687A8FD9DE38032121FDDBCC787F"
reaches bound inspect
employee name="Sam rng=52" reaches bound inspect
```

The first is a real baseline run digest. This is a scenario-field carrier, not an edited comparison object. A top-level scenario display-name payload did not reach `Steps` text, because these templates do not render it. Literal mixed-case `pRoJeCtIoN=17` was correctly refused. The benign employee name `Sam Branch` was also refused with `ErrBoundary`, illustrating the blacklist's false positives; which inspect ID reports the first failure can vary with map iteration.

`TestAuditRealizedOutcomeCarrier` goes further. It builds the real termination evaluation on the same mini/52 decision state, reads its proposal branch's `cash_at_horizon`, and copies the exact formatted value and horizon into the otherwise valid teleradiology request identifier. `Steps` then builds and binds its own comparison normally:

```text
evaluation-only value copied into valid requestId passes Steps:
cash at 2026-12-11T00:00:00 = -$134,867.02
```

Both arm messages and the proposal inspect answer contain that text. The projection is computed by the witness upstream, not secretly fetched by `Steps`; this distinction matters. It still falsifies the claimed unconditional boundary against evaluation information carried through allowed fields. The current recorded inventory itself showed no such contamination.

**Required remediation and owner policy:** make the hex check case-insensitive, but do not present that as sufficient semantic protection. Define which proposal/scenario fields are trusted and how they are kept free of evaluation data; minimize or replace opaque identifiers in displayed actions with an explicit reversible mapping; and validate the provenance of the fixed scenario/proposal inputs used at lock. Arbitrary strings can encode numbers and outcomes without banned words. If the owner intends only structural separation with trusted scenario/proposal text, narrow the claim explicitly and accept that threat model before lock. Otherwise stronger input-origin controls are required. Retain the binding check: it correctly prevents independent comparison edits, but cannot sanitize contaminated source data.

**Outstanding gates (N1):** `PRESENTATION_REVIEW.md` remains PENDING; D1–D6 remain decisions; the workflow, driver, reply schema and lock generator are deferred. This technical review does not complete the human presentation review or authorize a run.
