## 2. Findings, ranked by severity

No Blocking and no Major finding.

### R1 — Minor. The duplicate-key defence covers the preview object, not the `preview` key itself (or the response envelope); the documentation says "a key given twice in the engine's line"

* **Where:** `snapshot/agents/llm/llm_agent6.py:294` (`_duplicates(p, "preview", problems)` walks `p = answer["preview"]` only; `answer` is the response's `result`, read at `:290`); the reader marks duplicates at every level (`:155-179`), so the information is available but unused above `preview`. Claim: `docs/V0.12_CONSEQUENCE_INVENTORY.md` §4 "an object in the engine's line that gives a key more than once is unavailable"; `docs/V0.12_ACKNOWLEDGMENT.md` §2.4 "A key given twice in the engine's line also fails"; the audit response "A key given twice in the engine's line also fails."
* **Witness:** `scratch/witness/w_review.py` cases E1a/E1b, log `scratch/logs/w_review.log`: the result object written as `{"preview": <copy A>, "preview": <copy B>}`. E1b (copy A the real answer, copy B with `severanceCents: 1`): `status=qualifying`, item `severance.severanceCents: 1` listed, acknowledged, final check agrees, **submitted**. E1a (the reverse): the real values are listed and submitted. By contrast, a key twice *inside* the preview is refused anywhere (E2 `displacements[3]`, E3 `funding`, E4 `results[0]`, the revision's `test_12`, and `S4` on the real process: exit 1).
* **Why Minor:** Go's `encoding/json` cannot emit a duplicate key, so no engine build can reach this; the model cannot cause it; the value listed is the one the reader kept, and it is what the record stores. The gap is between the documentation's sentence and the code, and the remedy is one call: walk the whole `result` (or the whole response line in `Harness.request`) instead of `preview`. Alternatively narrow the sentence to "inside the preview".

### R2 — Minor. The maintainer's before-fix log was not produced by the committed test file

* **Where:** `scratch/maintainer-f1-before-fix.log` versus `snapshot/agents/llm/test_llm_agent6_fields.py:103-121` (`test_03`). The log lists subtests `[nan]`, `[inf]` and the four date subtests as separate ERRORs. In the committed test the `nan`/`inf` loop is not a subtest, and the `A6.json_loads` call before it is not guarded, so against a pre-repair module (no `json_loads`) the test aborts with one unlabelled ERROR before the date subtests run.
* **Witness:** `scratch/logs/reviewer-f1-before-fix.log` (the committed tests against the reconstructed pre-repair agent): `FAILED (failures=2, errors=26)`, one bare `ERROR: test_03_wrong_severance_type` and no `[nan]`/`[inf]`/date-subtest lines; `diff` against the maintainer's log shows exactly that difference and nothing else. The maintainer's statement "15 of the 18 failed or errored (01–13, 16 and 18)" is **confirmed** by the reconstruction: the same 15 tests, and only those, fail; 14, 15 and 17 pass.
* **Why Minor:** evidence hygiene; the claim it supports is true. The log should be regenerated from the committed test file (or labelled as from a draft).

### Notes (observations, no defect)

* **N1 — A non-finite number in any engine line ends the run.** `json_loads` refuses `NaN`/`Infinity` (`:170-179`); `Harness._read` turns it into `ExchangeError` (`:192-194`), which is not a `ValueError`, so `ask()`'s retry path (`:734`) does not swallow it: the process prints the error, writes `summary.json`/`usage.txt` and exits 1 without a decision record for that point. Witness F6/F7 (in-process) and `S3-nan-on-the-wire` (real process: `exit=1`, stderr `a line that is not JSON: NaN is not JSON`, no `decisions.jsonl`). Fail-closed; nothing is submitted. The failure is recorded in stderr and the harness's run status rather than in a `withheld` record. The engine cannot send a non-finite number. A JSON `1e400` is read as `inf` by Python without going through `parse_constant` (H6) and is then refused as "not an integer" (T3); same outcome.
* **N2 — A duplicate key in a *validate* answer is not checked live but breaks replay.** Live, the proposal is validated, acknowledged and submitted (the validate answer is not a consequence source); at replay against the same engine the re-run's answer is a `_Duplicated` dict and `same()` compares types strictly, so the replay is refused at `record.attempts[0].validation[0].answer` (P7). The decisions file itself is plain JSON. Unreachable from the engine; worth normalising validate answers as `assess()` normalises the preview (`:427`) if the reader is kept.
* **N3 — Integers beyond int64 are accepted.** `severanceCents: 10**20` is listed and must be acknowledged exactly (T1). The engine's fields are `int64`; it cannot send this. Not a defect.
* **N4 — Required-but-unlisted fields.** `endDate` and `displaced` of a termination are required (`:205-206`) though the model is not shown them; `displaced` feeds the consistency check (`:308`). Both are emitted by every engine build (`internal/api/api.go:1683,1691`, no `omitempty`), so no valid answer is refused; confirmed on all 13 recorded answers. `TelePreview.plan` is required only for `start` (E8: a cancel entry without `plan` and with `guaranteedCents: null` still reads, as the inventory says).
* **N5 — Whitespace-only text passes the `text` kind** (`:229`). For `employee` it still fails because the entry no longer matches the action (T5); for `plan`, `offer` or `appointment` a value such as `" "` would be listed. The engine cannot send one.
* **N6 — `_duplicates` walks the whole preview**, including `funding`, `forecast` and `results` (E3, E4). Broader than the consequence fields but fail-closed and consistent with the documentation.
* **N7 — Reconstruction of 82cea3f.** The pre-repair agent used in §4 is a functional reconstruction (`scratch/witness/make_prefix.py`, output SHA-256 `b09e10f0…`), not byte-identical to 82cea3f (`57ffad6b…`), because the diff was not given and the main repository was not touched. It reverts exactly what the response document describes (the `.get()` reads at the earlier audit's `:178-183`, `:196-198`, `:211-215`; `A3.Harness`; the unnormalised answer). Its contract and workflow identities equal the pinned ones, as the repaired file's do.
