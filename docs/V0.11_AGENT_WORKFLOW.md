# V0.11 agent decision workflow (`llm-agent-workflow/v1`)

Status: built in V0.11a (0.11.0-dev.1), unreleased. Implemented by
llm-agent 5 (`agents/llm/llm_agent5.py`) and tested deterministically with
scripted model replies only. No live model has been run with it. Whether
it improves decisions is V0.11b's question, not this document's.

**The principle.** Validate first. Preview selectively. Never treat an
accepted action as a recommended one.

## 1. Why

V0.10c found that the engine's validation answer and its preview change a
model's decisions in different ways:
* both corrected refused proposals much as well;
* at valid proposals, the preview tended to confirm them, including a
  $44,687.30 credit-supported commitment, which validation alone led the
  model to cut.

llm-agent 4 shows the preview before validation for every staffing
proposal. llm-agent 3 shows only a retry message after a refusal.

This workflow puts validation first. It returns the engine's own refusal
results, and shows the preview only for a valid proposal whose preview
shows a direct financial or capacity effect. Its wording says that
neither validation nor the preview endorses the decision. The design
follows the owner's V0.11 proposal; it is not tuned on V0.10b or V0.10c
outcomes.

## 2. The workflow

At each decision point (version 3's prompt, memory, settings and parser,
unchanged):

1. **The model proposes.** The details turn works as in version 3.
2. **Every batch is validated.** The proposal is split into version 3's
   batches (operations, then staffing), and `validate` is called for
   each. Every answer is recorded.
3. **If any action is refused,** the model gets the validation feedback
   (§3) and replies again: revise, or `"actions": []`. Nothing is
   rewritten for it.
4. **The revised proposal** goes back to step 2.
5. **If the proposal is fully valid and has staffing actions,** their
   `preview` is requested (read-only), once per decision point, for the
   first fully valid proposal with staffing actions.
6. **If the preview is eligible** (§4) and fits the prompt's bound, it is
   shown exactly as returned (§5).
7. **The model keeps, revises or abandons the proposal.**
8. **The reply is validated again** (step 2). A refusal goes to step 3.
   A revision is not previewed again.
9. **Only the final, fully validated proposal is submitted,** as version
   3's batches. Just before, the digests are asked again. If validation
   or preview changed the state, which they must not, nothing is
   submitted and the error is recorded.
10. **Otherwise nothing is submitted:** the outcome is `no_action` if the
    model chose no action, or `fallback` when the retry budget or the
    decision budget runs out.

**Retry budget:** `maxRetries` from the settings file (0–3). Every
refusal, unreadable reply or protocol error counts against it. The
preview review does not.

**Model requests at most per decision point:** 1 + `maxRetries` + 1
(preview) + 1 (details). A refusal never becomes an accepted action:
* the used attempt must have every batch validated;
* the replay checks it.

**Operations actions** have no preview. They go through validation only.
When a proposal mixes both kinds, the staffing part is previewed and the
operations part is named in the preview message (§5).

## 3. Validation feedback (`llm-agent-validation-feedback/v1`)

After a refused proposal the model is sent:

```
VALIDATION. Nothing has been submitted. The simulator refused actions in your reply. Its results for the refused actions, exactly as it returned them:
{"action":<number in the reply>,"result":<the simulator's result>}
…

Reply with one JSON object {"reason": ..., "actions": [...]}: changed actions to revise your reply, or "actions": [] to submit nothing. Your reply is validated again before anything is submitted.
```

* One line per refused result of every batch, in batch order. Each holds
  the action as the engine read it, the stable code (`insufficient_funds`,
  `invalid_schema`, `notice_too_short`, `batch_rejected`, …), the exact
  message and the result's other fields.
* Accepted results are not listed; "nothing has been submitted" covers
  them.
* No advice is added. The engine's own message may state amounts (an
  `insufficient_funds` message gives the commitment and the headroom).
  That is the engine's text, not the agent's.
* A reply the parser rejects, and a protocol error, are answered with
  version 3's retry message, unchanged. A model timeout resends the same
  messages.

This differs from llm-agent 3's feedback. llm-agent 3 sends "Your reply
could not be used: refused: action i: code: message; …". The v1 feedback
carries the engine's whole result for each refused action, framed so that
a revision or abandonment is the model's explicit choice.

## 4. Preview eligibility (`llm-agent-preview-eligibility/v1`)

**What was inspected.** The preview's fields
([benchmark/v10c-dev/API_INVENTORY.md](benchmark/v10c-dev/API_INVENTORY.md)),
and the previews of the 19 valid staffing proposals in the V0.8c and V0.9c
recordings (`docs/benchmark/v10c-dev/points/inventory.json`).
* A valid batch's preview carries the funding test (`funding`) and, when
  something changes:
  * `guaranteed` and `forecast` money lines;
  * item details (`hires`, `terminations`, `rosters`, `allocations`,
    `teleradiology`);
  * slots and `displacements`.
* A money line the batch does not change is marked in its `when`; a
  roster change, for example, restates the contract guarantee "unchanged
  by the roster".

**The rule.** The preview is shown when any of these holds in the
engine's answer, in this order (each recorded as a reason):

| Reason | Field | What it captures |
|---|---|---|
| `commitment` | `funding.commitmentCents > 0` | a new commitment the engine's funding test measures; credit-supported commitments included |
| `obligation` | a `guaranteed` line whose `when` does not contain "unchanged" | a new or changed guaranteed obligation: retainers (a retained obligation to the earliest end), salary changes, severance, recruiting fees, the earliest lawful exit |
| `termination` | `terminations` non-empty | severance, notice, lost capacity |
| `displacement` | `displacements` non-empty | booked appointments that lose coverage |
| `capacity` | `slotsOpened`, `slotsClosed` or `hires` non-empty | a change in bookable capacity or headcount |

* **No dollar threshold.** Nothing in the fields establishes where
  "material" begins, so none was invented. Any nonzero measured effect
  qualifies. In the recordings, 17 of the 19 valid staffing previews
  qualify; the 2 that do not change nothing (an allocation already at its
  value).
* **Facts recorded with the decision, never used to decide:**
  * the commitment and headroom;
  * the undrawn credit;
  * whether the commitment needs credit (it exceeds the headroom without
    undrawn credit);
  * the number of displaced bookings and terminations.
* **Statuses:**
  * `shown`;
  * `not_eligible` (no reason): the validated proposal is submitted
    without a preview turn;
  * `too_large` (the message would exceed `maxPromptChars`): not shown,
    submitted as validated;
  * `failed` (a protocol error): recorded, submitted as validated.

  The preview is read-only. The digests are checked after it.

## 5. Preview presentation (`llm-agent-selective-preview/v1`)

```
PREVIEW. The actions in your reply passed validation: the simulator would accept them now. Nothing has been submitted yet. This is the simulator's preview of the staffing actions in your reply (actions …), exactly as the simulator returned it. It describes their direct commitments and effects:
<the preview answer, compact JSON>

[The operations actions in your reply also passed validation; the simulator has no preview for them.]

Passing validation and this preview do not establish that the decision is beneficial. Reply with your final decision, one JSON object {"reason": ..., "actions": [...]}: the same actions to keep it, changed actions to revise it, or "actions": [] to submit nothing. Your reply is validated again before anything is submitted.
```

The message:
* says the proposal passed validation, and what that means ("would
  accept them now");
* says the preview describes direct commitments and effects;
* says neither establishes that the decision is beneficial;
* offers keep, revise or abandon.

It adds no strategy, no recommendation and no risk score.

## 6. Mixed batches

The simulator's batch semantics are unchanged.
* Operations and staffing actions are separate batches, operations first
  (version 3's split).
* Each batch is validated at the decision point's state, independently.
  There is no cross-batch atomicity: the harness applies the batches in
  order, and a batch refused at apply changes nothing.
* The agent cannot see apply results within its turn; the harness records
  them (`decisions.json`). At the next decision point the agent reads the
  engine's action log in its observation and records the previous
  point's execution (§7, E):
  * each submitted batch matched to its logged results, in order, by
    action types;
  * a batch with no log entry recorded as not applied. A refused batch
    leaves no log entry; its results are in the harness's record.

  Nothing is rolled back or retried.

## 7. The record (`dreamteam.llm-decision-record/v5`)

Version 3's record, with the workflow's versions
(`workflowVersion`, `workflowSha256`: the SHA-256 of the workflow version,
both templates, the operations note and the eligibility rule) and:

| Stage | Where |
|---|---|
| **A. Proposed** | each attempt's output (SHA-256, length, bounded text), parse, reason and actions; `stages.proposed` |
| **B. Validated** | each attempt's `validation`: every batch, its indices and the engine's whole answer; `refusals`; `stages.validated`, `stages.refused` |
| **Feedback** | the next attempt's `input`: kind `validation` (v1 feedback, by SHA-256 and length), `retry` (version 3's message, with the error), `resend` or `details` |
| **C. Previewed** | the attempt's `preview`: actions, indices, status, the engine's answer and its SHA-256, error, eligibility (version, reasons, facts), `digestsUnchanged`, the message's SHA-256 and length; the reply's input kind `preview`; `stages.previewed` |
| **D. Submitted** | `batches`, `outcome`, `final` (the used attempt); `stages.submitted`; `digestsBeforeSubmit.unchanged` |
| **E. Executed** | the next point's `previousExecution`: per submitted batch, applied or not, and the engine's logged results. The last point's execution is in the harness's `decisions.json` only |

* **Inputs and memory:** `promptSha256`, `memorySha256` and each input's
  SHA-256.
* **No discarded attempts:** every model request is an attempt, recorded
  as it is made (`attempts.jsonl`).
* **No secrets:** no API key or endpoint in the record (the evidence's
  `agent.json` names the endpoint, as version 3's does).

**Replay** (`--replay FILE`) needs no model. It checks:
* the memory, the prompt, and every input message rebuilt (prompt,
  details, validation feedback, preview message, retry);
* every `validate` and `preview` asked again and compared;
* the eligibility recomputed;
* the refusals, used attempt, batches and stages;
* the state check;
* the previous point's execution, read again from the observation.

Version 5 replays only version 5 records; earlier versions replay with
their own agents.

## 8. Deterministic test evidence

* **`agents/llm/test_llm_agent5.py`:** 29 tests, scripted model and
  engine. They cover the owner's 24 items:
  * valid without preview, and with preview kept, revised or abandoned;
  * refused then corrected or abandoned; repeated refusals; a revision
    that fails;
  * insufficient funds; a credit-supported commitment; a retained
    obligation; displaced bookings;
  * mixed batches, including an operations refusal;
  * the preview too large or failing; a model timeout; unreadable output;
    the retry budget;
  * recording completeness; model-free replay with tampering refused;
    compatibility; deterministic output;
  * the no-state-change guard.
* **`internal/bench/llm_agent5_test.go`:** the real engine and harness,
  with the mock model server.
  * Five behaviours: keep, revise and abandon after the preview; refused
    then fixed; mixed operations and staffing.
  * Only validated batches are submitted, and the harness applies them.
  * The next point records them executed.
  * The replay matches the live run byte for byte without a model.
  * Tampered validation answers, a dropped preview and a version 4
    recording are refused.
* **`docs/benchmark/v11a-dev/scripted-cases.json` and `.md`** (made by
  `analysis/workflow/scripted_cases.py`): every scripted case's record.
  CI regenerates them and compares them on every platform.

## 9. Known limitations

* **Not evaluated.** No live model has run this workflow, and nothing
  shows it improves decisions. V0.11b is to test that, including whether
  the preview message still encourages keeping expensive commitments.
* **Coverage:**
  * one preview per decision point, for the first valid staffing
    proposal; a revision after it is validated, not previewed;
  * eligibility has no threshold, so most valid staffing proposals with
    any effect are previewed;
  * operations actions have no preview: a paid shift extension's cost
    appears only in the engine's validation message.
* **Bounds:**
  * a preview larger than `maxPromptChars` is not shown (recorded as
    `too_large`);
  * the action log in the observation keeps the latest 20 entries, so a
    previous point with more actions cannot be matched in full;
  * the last point's execution is in the harness's record only.
* **Not llm-agent 3's feedback.** The validation feedback is new text;
  the agents' earlier recordings are not comparable message for message.
* The independent evidence review remains **PENDING**
  ([REVIEWER_HANDOFF.md](REVIEWER_HANDOFF.md)).
