# V0.13l recording specification

Driver `dreamteam-v13l-driver/8`; manifest `dreamteam.alternatives-run/v8`; analysis `dreamteam.alternatives-analysis/v9`; partial-run procedure /8; lifecycle /4; evidence bindings /2; strict JSON `dreamteam.strict-json/v1`; response handoff `dreamteam.response-handoff/v1`; failure retention `dreamteam.failed-persistence-retention/v2`. Engine `0.13.0-dev.2`, draw /4, call journal /1, health observation /2, failure event /3, public result /1, completed-draw handoff /1 and completion seal /1 retain their formats. [Contract identities](CONTRACT-IDENTITIES.json) pin the successor implementations.

The archive retains `run.json`, `draws.json`, `calls.jsonl`, optional `server-before.json`, `aborted-draw.json`, `failure-event.json`, and the sole completion marker `SEAL.json`. A valid seal is required but insufficient: FULL analysis validates every relationship and replays every reconstructable event.

**Model calls.** Each call passes four phases. *Dispatched*: the dispatch intent is appended and fsynced before the transport is invoked. *Received*: the transport's result is assigned to the recorder (`received`) in the statement that receives it. *Recorded*: the returned (or raised) outcome is appended and fsynced; the journal append now closes its descriptor through the injectable filesystem, so a close failure is also a recording failure. *Consumed*: only then is the response returned to the workflow. If recording fails, the archive is poisoned, the draw ends at once with `ResponseNotRecorded` (a `BaseException`, so no workflow handler converts it into a retry), no replacement call is made and the call budget is unaffected; the received outcome is kept in `receivedResponses`. The aborted draw's partial evidence then shows the recorder's refusal as its last client error, while `receivedResponses` holds the response actually received.

**Completed draws.** `pending-draw.json` contains `{schema, draw, rowSha256}`; it is written and fsynced before the ledger changes and removed only after a durable ledger commit and `commit_draw`. The returned result is assigned to the recorder in the receiving statement; the handoff is inside the same recovery scope. A handled exception that escapes run_draw after the workflow and final digests completed recovers the result from run_draw's frame and completes only run_draw's own deterministic bookkeeping. Handled reconciliation then commits the result (`reconciled: true`) followed by a driver stop, or, if persistence has failed, the archive is INVALID with the result retained.

**Failure retention.** `persistence-failure.json` (`failed-persistence-retention/v2`) contains `{schema, stage, error:{type,message}, pending, partialDraw, receivedResponses, dispatched, candidates}`; the identical document is attached to `RecordingError.retainedEvidence`. It is written best-effort without hooks, poisoning checks or candidate deletion, and never replaces the primary error. These artifacts are audit evidence for INVALID archives, never part of a sealed COMPLETE or PARTIAL archive.

All evidence uses the strict archive JSON parser. Only external causes may remain UNVERIFIED. No run resumption, inference authorization or protocol lock is provided. See the [partial-run procedure](PARTIAL_RUN_PROCEDURE.md) and [lifecycle contract](LIFECYCLE_CONTRACT.md).
