## 1. What the safeguard is, and is not

The safeguard works at the agent workflow layer. A proposal that
contains a high-impact action is not submitted until the model states,
for that exact proposal, each consequence the engine reports, with the
engine's exact values. The model may then submit it, revise it or submit
nothing.

* **Acknowledgment is not approval.** An acknowledgment records that the
  model stated the engine-reported direct consequences of the exact
  proposal.
* It does not establish that the action is clinically or financially
  wise.
* The engine reports direct consequences, not all possible future
  outcomes. The safeguard does not predict long-run profit, patient harm
  or any outcome the engine does not report.
* There is no automated recommendation, composite score or threshold. A
  valid action is never blocked because its consequences are large. The
  safeguard requires informed confirmation. It is not a management
  policy.
* The simulator's action rules are unchanged. The engine accepts or
  refuses an action exactly as before. The safeguard decides only whether
  the agent submits.
* A model can acknowledge that a termination displaces 100 appointments
  and still proceed. That is the intended behaviour, not a defect.
  Whether the safeguard changes decisions, or becomes a procedure that
  models learn to repeat, is a question for V0.12b.

## 2. The contract (`dreamteam.action-acknowledgment/v1`)

### 2.1 What qualifies

The qualifying conditions are read from the engine's `preview` of a
valid staffing batch. Each is class A or B in the inventory. No dollar
threshold is used.

| Condition | Item | Exact values required |
|---|---|---|
| Termination | One per `terminate` action, matched by `employee` to `preview.terminations[]` | `termination.lastDay`, `termination.noticeDays`, `severance.severanceCents`, `severance.severancePayday` |
| New retained obligation: a hire | One per `hire`, matched by `requestId` to `preview.hires[]`; its fee and exit are the guaranteed lines in the engine's documented position, with their labels checked | `retained_obligation.recruitingFeeCents`, `retained_obligation.earliestExitCents` |
| New retained obligation: a teleradiology start | One per `contract_teleradiology` with op `start`, matched in order to `preview.teleradiology[]`, with op, plan and effective date checked | `retained_obligation.guaranteedCents`, `.guaranteedThrough`, `.minimumTermEnd` |
| Displaced bookings | One per staffing batch with `preview.displacements`. The target is the batch; the count is never attributed to one action. | `displaced_bookings.count` |

Everything else is ordinary and is submitted as validated:
* a salary allocation change, which is withdrawable at no cost until
  notice;
* a roster change that displaces nothing;
* a teleradiology cancellation, which fixes the end of an existing
  obligation;
* operations actions.

### 2.2 Items

Items are numbered `C1`, `C2` and so on: the action items in reply
order, then the batch item. The model sees each item as one line of
compact JSON:

```
{"id":"C1","action":1,"type":"terminate","target":"E03","consequences":{"termination":{"lastDay":"2026-11-02","noticeDays":20},"severance":{"severanceCents":360000,"severancePayday":"2026-11-13"}}}
{"id":"C2","actions":[1],"type":"staffing_batch","target":"staffing batch","consequences":{"displaced_bookings":{"count":3}}}
```

The record also keeps each item's `source`: the path in the engine's
answer it was read from.

### 2.3 The payload and its token

The payload is `{"contract", "proposal": the exact actions, "items"}`.
Its hash is SHA-256 over canonical JSON (sorted keys, no whitespace), so
the same proposal written with its keys in another order is the same
proposal. The **token** is the first 16 hex digits of that hash. It names
the proposal in the request, and the acknowledgment must quote it.

### 2.4 An acknowledgment

The reply to a request is the decision object, plus `"acknowledgment"`:

```json
{"reason": "...", "actions": [the same actions],
 "acknowledgment": {"proposal": "<token>", "items": [<one entry per item>]}}
```

The acknowledgment is accepted only if all of these hold:
1. The reply answers the request for the same proposal: its actions
   equal it exactly. A reply with changed actions is a new proposal, and
   any acknowledgment in it is recorded as `proposal_changed` and never
   accepted.
2. `acknowledgment` is an object with exactly `proposal` and `items`.
   Anything else, such as "I understand." or `{"understood": true}`, is
   `malformed`. A reply with no acknowledgment, including agreement
   stated in `reason`, is `missing`.
3. `proposal` is the request's token. A token of an earlier proposal at
   the same decision point is `stale_proposal`; any other token is
   `wrong_proposal`.
4. There is exactly one entry per required item, and nothing else
   (`missing_item`, `unknown_item`, `duplicate_item`, `malformed_entry`).
   An entry has `id`, `action` (or `actions` for the batch item), `type`,
   `target` and `consequences`, and no other key.
5. Every field equals the engine-reported value exactly, with the same
   JSON type:
   * the action number (`wrong_action`);
   * the type (`wrong_type`);
   * the target (`wrong_target`, for example another employee);
   * the consequence types (`wrong_consequence_types`) and their fields
     (`wrong_consequence_fields`);
   * each value (`wrong_value`). `360000.0`, `"360000"` and `true` are
     not `360000`.

   The engine-reported values are taken as the engine sends them. The
   workflow relies on the engine's preview contract
   (`internal/api/api.go`) for which fields are present and their JSON
   types. At engine 0.12.0-dev.1 every one of these fields is always
   present and has the documented type. The workflow itself does not
   check this. If a future engine left a field out, or sent it with
   another type, that value would be listed and matched as received:
   `null`, or a string. A reply restating it would then be accepted. The
   independent audit reported this as F1, and §9 covers it.

Every failure is listed. Nothing is accepted unless there are none.

## 3. The workflow (`llm-agent-acknowledgment-workflow/v1`)

At each decision point:
1. **Propose.** Version 3's prompt, memory and parser are unchanged. A
   reply may also carry `acknowledgment`, which is taken out before
   version 3's strict parser.
2. **Validate.** Every batch is validated. A refusal is answered with the
   simulator's results, using version 5's validation feedback unchanged.
3. **Read the consequences.** For a fully valid proposal with staffing
   actions, the staffing batch is previewed and the items are read (§2.1).
   A proposal with no items is submitted as validated.
4. **Request acknowledgment** (`llm-agent-acknowledgment-request/v1`).
   The message:
   * says nothing has been submitted;
   * lists the items with the token;
   * says these are direct consequences, not all future outcomes, and
     that acknowledgment is not approval and does not establish that the
     actions are wise;
   * gives the reply's form.

   The model may acknowledge, revise (the revision is validated and
   assessed again, with a new request and token) or reply
   `"actions": []`.
5. **Match** (§2.4). A rejected acknowledgment is answered with
   `ACKNOWLEDGMENT NOT ACCEPTED`, every failure, and the request again.
6. **Final check.** After an accepted acknowledgment, every batch of the
   acknowledged proposal is validated again, and the staffing batch is
   previewed again with its items recomputed. The validate answers, the
   preview answer's hash and the payload hash must equal those
   acknowledged, with the state digests unchanged.
7. **Submit,** only when the acknowledgment and the final check both
   pass, and after the usual check that the state did not change during
   the decision.

**Retry budget.** These count against `maxRetries`:
* a refusal;
* an unreadable reply;
* a rejected acknowledgment;
* a revision given in answer to an acknowledgment request.

A first acknowledgment request does not count, any more than V0.11a's
preview did. A timeout resends the same messages, as before.

## 4. Fail-closed behaviour

A qualifying proposal is never submitted without an accepted
acknowledgment and an agreeing final check. Nothing is submitted, and
`withheld` records the attempt, each batch, whether it needed
acknowledgment, its items and the reason, when:
* the acknowledgment is missing, malformed, unparseable, incomplete,
  contradictory, for another action or for an earlier proposal, and no
  retry is left (`acknowledgment_not_accepted`, with the last failure);
* the consequences cannot be read reliably (`consequences_unavailable`).
  This covers a preview protocol error, a preview that does not accept
  what validation accepted, a termination, hire or teleradiology action
  with no matching entry, guaranteed lines out of the engine's order, or
  a state change during the preview. A staffing proposal whose preview
  fails is withheld even when no action in it is known to qualify,
  because displacement cannot be ruled out;
* the final check disagrees (`final_check_disagrees`);
* the decision's time budget runs out while acknowledgment is pending.

The proposal is never rewritten or approved automatically. In
particular, when a qualifying staffing batch is withheld, the proposal's
operations batch is **not** submitted on its own: that would submit a
proposal the model did not make. The acknowledgment is never bypassed.

## 5. Mixed batches

The simulator's batch semantics are unchanged:
* operations and staffing actions are separate batches;
* the operations batch is applied first;
* the two batches are **not atomic**. The engine can apply one and
  refuse the other at submission, as before. Nothing here claims
  cross-batch atomicity.

Every qualifying action in the staffing batch has its own item. An
acknowledgment of one action is never taken as acknowledgment of
another, or of the batch. The displaced-bookings item belongs to the
batch as a whole. The final check validates both batches again. If any
required acknowledgment fails, no batch of the proposal is submitted,
and `withheld` lists each one (operations: not qualifying; staffing:
qualifying, with its items).

## 6. The record (`dreamteam.llm-decision-record/v6`)

The record is version 5's record (llm-agent 3's fields and version 5's
validation and execution fields), with these additions:

| Field | What it holds |
|---|---|
| `workflow`, `workflowVersion`, `workflowSha256`, `contract`, `contractSha256` | The identity. Replay refuses any other. |
| `retryBudget` | `maxRetries` and `decisionBudgetSeconds`. Replay runs with them. |
| `attempts[].output.text` | The model's reply in full, not cut. It contains the acknowledgment as the model wrote it. |
| `attempts[].validation` | Each batch's validate request (actions, indices) and answer. |
| `attempts[].assessment` | The consequence reading:
* `actions`, `indices`;
* the engine's preview `answer` and `answerSha256`, or `error`;
* `items` (each with `source`) and `problems`;
* `payload` (`sha256`, `token`);
* `digestsUnchanged`;
* `status`: `ordinary`, `qualifying` or `unavailable`. |
| `attempts[].input` | The message answered: `prompt`, `details`, `validation`, `retry`, `resend`, `acknowledgment` (with the token) or `acknowledgment_rejected`, by SHA-256. |
| `attempts[].acknowledgment` | `forAttempt` (the proposal it answers), `proposal` (the token), `present`, `given` (the acknowledgment as parsed), `match` (`accepted`, `failures`). |
| `attempts[].finalCheck` | The final validate answers, the preview's and payload's hashes, `digestsUnchanged`, `agrees`, `differences`. |
| `withheld` | §4. |
| `batches`, `final`, `digestsBeforeSubmit` | What was submitted, as in version 5. |
| `stages` | `proposed`; `validated` (every validate answer valid); `refused`; `previewed` (the consequences read); `acknowledgmentRequested`; `acknowledged`; `submitted`. **Executed** is read at the next point (`previousExecution`, version 5's). |

No attempt is discarded: every model call is an attempt in the record.
The model's request messages, usage and latency are in `model.jsonl`, as
before. The record holds no endpoint, key or system prompt.

## 7. Replay

`llm_agent6.py --replay FILE` contacts no model. For each recorded
decision point, it runs the same workflow code again against the engine,
with each attempt's recorded reply, or its recorded transport failure, in
place of the model. A reply's text must match its recorded hash. The
re-run:
* rebuilds every message;
* asks validate and preview again;
* recomputes the items, payload and token;
* matches every acknowledgment again;
* repeats the final check;
* produces the submitted batches.

The new record must equal the recorded one in every field (apart from
`mode`). The first difference is named, and the replay is refused. So
partial tampering is rejected: an edited consequence value, payload
hash, parsed acknowledgment, match result, stage or submitted action; a
reply text that no longer matches its recorded hash; or a removed or
reordered attempt.

**What replay proves, and what it does not.** Replay certifies
consistency: given the recorded replies, this workflow and this engine
produce exactly this record. It does not certify who wrote the replies.
A reply's text is checked only against its own recorded hash. A record
can therefore be regenerated consistently from hand-written replies. It
would replay as accepted. The same holds when one reply is replaced and
every field derived from it is updated. (The independent audit, F2,
demonstrated both.) Replay cannot distinguish a reply the model sent from
one a person wrote. Neither the record nor the replay authenticates the
model's output. The run's `model.jsonl` (the requests sent, usage and
latency) is the record of the model calls, and must be kept with every
run. Replay does not cross-check it. A record with
another workflow or contract identity, or a version 5 record, is refused
at load. llm-agent 1 to 5 recordings replay with their own agents,
unchanged.

* **`agents/llm/test_llm_agent6.py`:** 31 tests, scripted model and
  engine. They cover the 29 behaviours the milestone named, numbered
  `test_01`–`test_29`, and two more:
  * the items read from 13 distinct real engine preview answers recorded
    in V0.11b. These include terminations with up to 100 displaced
    bookings, one hire (the class B derivation), teleradiology starts and
    allocation changes;
  * the pinned identities.

  Every scripted case also replays without the model to an identical
  record.
* **`internal/bench/llm_agent6_test.go`:** the real engine and the mock
  model, two seeds:
  * a termination acknowledged and submitted;
  * a teleradiology start (a retained obligation) acknowledged and
    submitted;
  * several terminations in one batch, each acknowledged;
  * a generic "I understand." that withholds the termination.

  The engine applies every submitted batch. Every item's value is
  checked against the engine's own answer. The replay is byte-identical
  to the live run without a model call. A tampered value, acknowledgment
  or action, and a version 5 recording, are refused.
* **`internal/bench/llm_agent6_displacement_test.go` (V0.12b Stage
  A):** the real engine, at a decision point where terminations displace
  bookings. It checks the exact batch count, each termination's own item,
  a missing or wrong displacement acknowledgment withholding the
  proposal, and a changed proposal needing its own acknowledgment. It
  also checks that the final re-preview matches, that applying displaces
  the acknowledged number, and that replay is byte-identical. See
  `docs/benchmark/v12b-dev/DISPLACEMENT.md`.
* **`docs/benchmark/v12a-dev/scripted-cases.{json,md}`:** 27 scripted
  cases, made by `analysis/acknowledgment/scripted_cases.py`. CI makes
  them again and compares them on linux/amd64, linux/arm64 and
  darwin/arm64.

## 9. Known limitations

* **Scripted models only.** No live model has seen the request. Whether
  models acknowledge accurately, whether the safeguard changes
  decisions, and whether acknowledgment becomes a repeated procedure are
  untested (V0.12b).
* **Restating values is not understanding.** The request lists the exact
  values, so a matching acknowledgment shows that the reply reproduced
  them for the right actions and proposal. It does not show
  comprehension or judgement.
* **Displacement is a batch fact.** The engine does not attribute
  displaced bookings to individual actions, and neither does the
  safeguard.
* **A hire's fee and exit amounts are class B.** They are read from the
  engine's documented line order and checked against the line labels. A
  change to that order makes the consequences unreadable, and the hire
  is withheld rather than misread.
* **The engine's preview contract is trusted (audit F1).** The workflow
  does not check that each consequence field is present in the engine's
  answer, or that it has the documented type. At this engine revision it
  always is. Proposed hardening, pending an owner decision: a missing or
  mistyped field makes the consequences unavailable, so the proposal is
  withheld.
* **Replay certifies consistency, not authorship (audit F2).** See §7.
* **Real-engine hire coverage is thin (audit F4).** No Go test runs a
  hire on the real engine. The class B derivation is checked on the one
  recorded real answer that contains a hire, and on the scripted engine.
* **Real-engine displacement is covered at small scale.** The mini
  scenario's displacements are 7 to 22 bookings
  (`docs/benchmark/v12b-dev/DISPLACEMENT.md`). The 100-booking case
  appears only among the recorded V0.11b answers. The count is compared
  exactly at any size.
* **Direct consequences only.** Whether a displaced patient accepts a
  replacement, lost revenue, long-run profit, patient harm and clinical
  outcomes are not reported by the engine and are not part of the
  acknowledgment.
* **Operations actions have no preview.** They are never high-impact
  under this contract.
* **No cross-batch atomicity.** This is unchanged from V0.11.
* **Independent review.** The safeguard was reviewed independently in
  V0.12b Stage A (`docs/audits/v0.12b-safeguard-audit.md`): GO, with
  no blocking finding. The separate frozen 98-item evidence review is
  still PENDING.
